# 障害・エラー修正の起票（推奨）

深い原因分析をやり切ってから起票しない。**再現が書ける最小確認のあとすぐ親を作る。**

## 親の範囲（ハブ）

親 description に次を含める（Bug テンプレと併用可）:

- **現象**: 何が起きるか（ユーザー／テストから見えること）
- **確認の芽**: いま分かっている再現の手がかり（1回試した事実まで。原因断定は不要）
- **範囲**: 現象確認 → 調査 → 解決（親の完了は「現象が解消したこと」）
- **分割候補**: 確認 / 調査 / 解決（直後の `ticket-split` で子化）

起票前にやってよいこと: ログ1枚・再現1回・期待と実際の対比。  
起票前にやらないこと: 広範なコード読破、複数仮説の検証、修正の試し撃ち。

## 推奨する子（`ticket-split`）

| 子 | 役割 | 完了の目安 |
|----|------|------------|
| 現象確認 | 再現手順を確定し、失敗の証拠を残す | 再現手順＋期待／実際が検証可能 |
| 調査 | 原因仮説と根拠（修正はしないか最小PoCまで） | 仮説と根拠がジャーナル／本文に残る |
| 解決 | 修正＋検証 | 現象確認子の DoD を満たす |

依存: 確認 → 調査 → 解決（`precedes` 等）。親はハブ専用（親に実装着手しない）。

トリガ A–F や子の合格ラインは `ticket-split` の `policy.md` に従う。障害でも調査と実装の同居（広い修正＋原因洗い）は分割必須になりやすい。
