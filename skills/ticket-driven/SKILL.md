# チケット駆動開発 (Ticket-Driven Development)

Redmine チケットを起点に開発タスクを駆動する。

## HARD GATE（最優先）

次を満たすまで **コード変更・コミット・PR をしない**。

1. `issue_id` がある（ユーザー指定 or `ticket-create` で作成）
2. **要件が充足**され、完了条件が **検証可能**（充足の中身は `ticket-refine`。例: 範囲とテストがあり、`cargo test` 成功）
3. **分割判定が済んでいる**（機能構成単位で子チケット作成済み、または分割不要と判定済み）
4. 着手ジャーナル 1 行を書いた（実装するチケット＝子がある場合は **子** に書く）

**自動精緻化（人手を待たない）**: 着手・実装要求の時点で、ユーザーに確認せず **先に `ticket-refine` で要件充足を判定**する。欠けていれば description を更新してから次へ進む。DoD が検証可能でも、範囲・失敗時・テストが足りなければ更新する。充足済みなら更新はスキップする。

**自動分割（精緻化の直後）**: 精緻化が済んだ、または充足済み（更新スキップ）のあと、実装の前に必ず **機能構成単位で `ticket-split` を判定・実行**する。分割後は **子チケットを作業単位**とし、親は進捗・統合のハブにする。単一の機能構成に収まるときだけ分割をスキップする。

refine 後も DoD が書けない／外部情報が必須 → 質問は **最大3つ**に絞る。それ以外は止めず完走する。

例外: 質問・設計のみ／読み取り調査のみ／ユーザーが「チケット不要」と明示。

起動フレーズ例: `#42 着手` / `#42 レビューして`

## 日常最小フロー（デフォルト・自動完走）

大きい儀式はしない。途中で許可を求めず、ブロック要因がなければ最後まで進める。

```
get(#N)
 → ticket-refine（要件充足。足りていれば更新スキップ）
 → ticket-split（機能構成単位・確認不要）
     ├ 分割する → 子を作成し、子ごとに着手〜完了。親は done_ratio / 最終 Resolved
     └ 分割不要（単一機能構成）→ 当該チケットで着手〜完了
 → 着手ノート + In Progress
 → テスト計画の確認（漏れ拾い。足りていれば本文を書き直さない）
 → 実装（リファクタ意識・予防。code-refactor に従う）
 → テスト計画の実行 + 完了条件の検証
 → code-refactor 事後検討（触ったファイルのみ・セーフティネット・確認不要）
 → 完了ノート + Resolved
 → ユーザーがコミット/PR を求めたらそのときだけ
```

| タイミング | ジャーナル |
|-----------|------------|
| 精緻化（自動時） | `精緻化: {要約}`（refine 側。充足済みなら「更新なし」） |
| 分割 | `チケットを分割: ...`（split 側） |
| 着手 | `着手: {概要}`（実装チケット＝子優先） |
| テスト計画 | `テスト計画: {要約}`（新規作成・大幅補完時のみ） |
| テスト実行 | 完了ノートに含めてよい（`完了: ... — テスト: {結果}`） |
| リファクタ（予防） | `リファクタ: 予防 — {要約}`（大きめの分割・浅化時のみ） |
| リファクタ検討 | `リファクタ検討: {実施|見送り} — {要約}`（しきい値超過時のみ） |
| 完了 | `完了: {概要} — {検証結果}` |

進捗ジャーナルの連投は不要。詰まったときだけ追記。

### テスト計画の作成・実行（自動）

HARD GATE ではない。工程を増やさない。**テストファースト（先に失敗するテストを書く）は必須にしない。**  
合格ラインの正本は `ticket-refine` の「テスト範囲の合格ライン」。本ステップは **漏れ拾い** であり、計画を二度書かない。

#### 確認（実装前）

精緻化済みの「テスト範囲」を合格ラインで見る。

- 足りている → 本文を書き直さない。ジャーナルも不要
- 無い／完了条件の言い換えだけ（`cargo test` のみ等）／自動・手動・目視が分からない → **確認せず既存欄を直す**

分割後は **子の完了条件に対応した計画** を子に書く。親の薄いテスト範囲をコピーしない。

契約が明確なバグ修正・純粋ロジックでは、失敗するテストを先に書いてもよい（任意）。

#### 実行（実装後）

1. テスト計画どおり実行する
2. DoD（完了条件）もあわせて検証する
3. 失敗したら直して再実行。Resolved にしない
4. 完了ノートに結果を1行含める

ドキュメントのみ・読み取り調査のみなど、実行手段が無い変更は「目視確認」を計画に書いて実行扱いにしてよい。

### リファクタ意識の実装（実装中・自動）

実装は機能追加だけでなく、**書きながら肥大化・深いネストを避ける**。詳細は `code-refactor` の「実装中の予防」。HARD GATE ではない。

実装中にやること（確認不要）:

1. **触る前に一瞥**: 既存ファイルの行数・ネストがしきい値近くなら、足す前に分割／浅化の置き場所を決める
2. **増やさない書き方**: early return、小さな関数、責務の境界を最初から意識する（あとで直す前提の巨大ブロックを書かない）
3. **超えそうなら同チケットで小さく直す**: 今回の差分が 600行超／ネスト5超を押し上げるなら、振る舞いを変えずにその場で分割・浅化してよい
4. **バグ修正と混ぜない**: 仕様変更とリファクタはコミット／差分の意図を分けられる単位にする（同一チケット内でも論理は分ける）

ジャーナルは通常不要。予防で大きめの分割をしたときだけ `リファクタ: 予防 — {要約}` を1行。

### リファクタ検討（実装直後・セーフティネット）

テスト実行・DoD 検証のあと、**今回触ったソースだけ** `code-refactor` を再検討する（リポジトリ全体スキャンはしない）。実装中の予防の漏れを拾う。HARD GATE ではない。実施必須でもない。

| しきい値 | 動作 |
|---------|------|
| 600行超 | 機能構成単位のファイル分割を **検討** |
| ネスト5超 | 階層浅化を **検討** |

- 詳細手順・見送り基準は `code-refactor`（`skills/code-refactor/SKILL.md`）に従う
- 小さい変更なら同チケット内で実施してよい（振る舞いを変えない）
- 大きい／別責務ならフォロー or 子チケットにし、本チケットの Resolved は止めない
- しきい値未満ならジャーナル不要。超過時のみ上記テンプレで1行

## いつ重い手順を使うか（自動判定）

| 条件 | 動作 |
|------|------|
| 要件不足、または完了条件が検証不能 | **自動で** `ticket-refine`（確認不要。充足済みなら更新スキップ） |
| 精緻化済、または充足済み（更新スキップ） | **自動で** `ticket-split` を判定。機能構成が2つ以上なら **子を作成してから**作業（確認不要） |
| すでに子チケットがある | 再分割しない。未完了の子を作業単位にする |
| 依存の明示が必要 | `ticket-relation`（`precedes` / `blocks` 等） |
| テスト範囲が無い／曖昧／DoD の言い換えだけ | **自動で** 既存のテスト範囲を直す（漏れ拾い。新規に書き直さない） |
| 実装中 | **リファクタ意識**で書く（予防。`code-refactor`）。確認不要 |
| 実装完了後 | **必ず** テスト計画を実行し DoD を検証してから Resolved |
| 実装で触ったファイルが 600行超 or ネスト5超 | **自動で** `code-refactor` を事後検討（確認不要。実施は任意） |

判定は毎回行う。充足済みなら **更新だけ**スキップしてよい。**分割判定はスキップしない**（単一機能なら「分割不要」と判定して進む）。

### 分割後の作業順

1. 依存なし（先行）の子から着手する
2. 子のテスト範囲は子の完了条件に対応させる（親の計画をコピーしない）
3. 子を Resolved にするたびに親の `done_ratio` を更新する
4. すべての子が Resolved になったら親を Resolved にする（親に完了ノート）

## Redmine MCP 呼び出しの約束（この環境）

- `redmine_issues` は **`list` / `get` のみ**。作成・更新・ノートは **`redmine_api_request`**
- `issue` / `relation` / `body` / `query` は **オブジェクト**。JSON 文字列にしない
- `issue_id` は文字列（`"42"`）。誤って `id` キーを使わない
- `get` の `include` は **文字列配列**（`["journals","attachments"]`）
- list のフィルタは **`query` オブジェクト**へ
- 認証トークンは渡さない。MCP 非接続時は `./tools/redmine_helper.sh`（`REDMINE_API_KEY` 必須）
- HTTP 不通時は Redmine / DB コンテナ起動を先に試す

## ステータス（本環境の目安）

必ず `GET /issue_statuses.json` で確認すること。

| 意味 | よくある ID |
|------|-------------|
| 新規 | 1 |
| 進行中 | 2 |
| 解決 | 3 |

標準遷移: `New → In Progress → Resolved → Closed`（Feedback 経由あり）

## 最小操作例

取得:

```json
{ "action": "get", "issue_id": "42", "include": ["journals", "children"] }
```

ツール: `redmine_issues`

着手（ノート + 進行中）:

```json
{
  "method": "PUT",
  "path": "/issues/42.json",
  "body": { "issue": { "notes": "着手: APIリトライ", "status_id": 2 } }
}
```

完了:

```json
{
  "method": "PUT",
  "path": "/issues/42.json",
  "body": { "issue": { "notes": "完了: リトライ実装 — cargo test 成功", "status_id": 3 } }
}
```

ツール: `redmine_api_request`

## 完了条件の書き方

悪い例: 「品質を高める」「堅牢にする」  
良い例: 「`scripts/ci.sh` が通る」「`brave_search.rs` に 429 リトライが入り最大3回」

## コミットと PR

ユーザーが明示したとき、またはチケット完了条件に含まれるときだけ行う。  
安全手順は Cursor ユーザールール／`git-*` スキルに従う。PR 本文に `Refs: #N` を入れる（子の場合は子 ID。親にも触れたら親も列挙可）。

## Redmine 主要ツール

| ツール | 用途 |
|---|---|
| `redmine_issues` | list / get のみ |
| `redmine_api_request` | 作成・更新・ノート・statuses・relations 等の REST |
