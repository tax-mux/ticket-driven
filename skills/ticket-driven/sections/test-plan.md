# テスト計画の作成・実行

HARD GATE ではない。工程を増やさない。**テストファースト（先に失敗するテストを書く）は必須にしない。**  
合格ラインの正本は `ticket-refine` の `sections/sufficiency.md`（テスト範囲の合格ライン）。本ステップは **漏れ拾い** であり、計画を二度書かない。

## 確認（実装前）

精緻化済みの「テスト範囲」を合格ラインで見る。

- 足りている → 本文を書き直さない。ジャーナルも不要
- 無い／完了条件の言い換えだけ（`cargo test` のみ等）／自動・手動・目視が分からない → **確認せず既存欄を直す**

分割後は **子の完了条件に対応した計画** を子に書く。親の薄いテスト範囲をコピーしない。

契約が明確なバグ修正・純粋ロジックでは、失敗するテストを先に書いてもよい（任意）。

## 実行（実装後）

1. テスト計画どおり実行する
2. DoD（完了条件）もあわせて検証する。各項目の検証が、その項目の求める段階（`ticket-refine` の `sufficiency.md`「検証の強さ」）に届いているかを確かめる。届かないなら検証を足す
3. 失敗したら直して再実行。Resolved にしない
4. 完了ノートの `検証:` 欄に、DoD 項目ごとの証跡を書く（`close-audit.md`「検証証跡」）

ドキュメントのみ・読み取り調査のみなど、実行手段が無い変更は「目視確認」を計画に書いて実行扱いにしてよい。

## 新規の検証か、既存の検証の改修か

DoD 各項目について、裏付けが **新規に追加した検証** か **既存の検証を改修したもの** かを、完了ノートの `検証:` 欄で区別する（例: `- [x] {DoD} — 実行（新規）: …` / `— 実行（既存改修）: …`）。既存テストを新しい仕様に合わせただけで、DoD の中心観点を確かめる新規検証が無い状態を避けるため。

既存の検証の **期待値を反転・削除** したとき（仕様変更で正しくなった場合を含む）:

- それまでその検証が守っていた観点を書き出す（例: 「重複を拒否する」）
- その観点が新しい仕様でもまだ有効なら、**代わりに確かめる検証を追加**する（例: 拒否される条件が狭まったなら、狭まった条件で拒否されることを確かめる）
- 観点そのものが不要になったなら、その **理由** を完了ノートに1行書く

これは下記「失敗アサーション（禁止）」とは別の話である。あちらは **テストを通すために** 検証を弱めることの禁止。こちらは仕様変更で正しく書き換えたときに、失われた観点を補う義務。

UI・画面変更は追加で `ui-verify.md`。

## 失敗アサーション（禁止）

調査中でも次を **禁止**する。

- 失敗している expect / アサーションを **削除・タイムアウト延長だけで回避**する
- 「代替確認」（console.log / MCP 再照会のみ）に差し替えて **元の UI 検証を捨てる**
- テストを緑に見せるために DoD の検証対象を弱める

**許可**: 失敗箇所のままログ・スクショ・中間 assert を **追加**する。原因がテスト誤りと証明できたときだけ、テスト側を直す（その場合も完了ノートに根拠を書く）。
