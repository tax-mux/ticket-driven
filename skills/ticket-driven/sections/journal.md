# ジャーナル・タイミング

> **これはスキル内の書式説明書。** 作業ログの実体は **Redmine チケットの `journals`**（MCP get + `include: ["journals"]`）。
> プロジェクト内の `.ticket-driven/`、`journal.md`、`read_file` 探索は **しない**（SKILL.md「ジャーナルとは」）。

| タイミング | Redmine `notes` に書く文言 |
|-----------|------------|
| 精緻化（自動時） | `精緻化: {要約}`（refine 側。充足済みなら「更新なし」） |
| 分割（子を作った） | `分割: 機能構成→セッション完走` + 子 ID と題名の箇条書き（必須） |
| 分割不要（子を作らない） | `分割不要: {理由}`（**省略禁止**。下記フォーマット） |
| 評価依頼（別途評価エージェント定義時） | `評価依頼: {計画\|実装} — #{id} — 先方:{識別}`（分割直後＝計画、レビュー提出直後＝実装。詳細は `request-eval.md`） |
| 評価依頼失敗 | `評価依頼失敗: {計画\|実装} — #{id} — {理由}`（自己 `評価: 合格` で逃げない） |
| 再開検討（リプラン要否判定の直後・実装前） | `再開検討: リプラン={要\|不要} / 残りDoD={n} / 作業単位=#{id} / 根拠={…}`（`resume.md`） |
| 計画継続（リプラン不要と判定したとき） | `計画継続: 作業単位=#{id} / 根拠={着手 or 前回再開検討}` |
| リプラン（計画を書き直したとき） | `リプラン: {理由1行}`（refine / split のあと。edit の前） |
| 着手 | `着手: {概要}` ＋ **委任パック**（形式は `delegate-pack.md`。実装チケット＝**子優先**。子がある親には書かない）。2つ目以降の子では `再読: 親 #{id} journal #{journal_id}` を1行（`after-split.md`） |
| 転記確認（決定事項を反映したとき） | `転記確認: #{id} journal #{journal_id} と一致`（向きを持つ記述を転記・言い換えたとき。下記「決定事項の転記」） |
| 判断（設計上の選択をしたとき・方針を変えたとき） | `判断: {決めたこと}` ＋ 理由／却下／前提（下記「判断の記録」。選択の無い票では書かない） |
| テスト計画 | `テスト計画: {要約}`（新規作成・大幅補完時のみ） |
| テスト実行 | 完了ノートの `検証:` 欄に DoD 項目ごとの証跡として書く（種類・書式は `close-audit.md`「検証証跡」） |
| リファクタ（予防） | `リファクタ: 予防 — {要約}`（大きめの分割・浅化時のみ） |
| リファクタ検討 | `リファクタ検討: {実施|見送り} — {要約}`（しきい値超過時のみ） |
| レビュー提出 | `レビュー提出: {要約}` ＋ **`status_id`=レビュー**（実装検証後。進行中のまま解決しない）。定義時は続けて `評価依頼: 実装` |
| 差し戻し（評価不合格） | `差し戻し: 評価不合格 — {要約}` ＋ **`status_id`=進行中**（実装側が行う。評価側は status を触らない） |
| 完了 | `完了: {概要}` ＋ `検証:` 欄（DoD 項目ごとの証跡。未実行は `未実行: {理由}`）（評価合格後。クローズ監査に **評価済み=yes**） |
| 評価（`ticket-evaluate`） | `評価: {合格\|条件付き合格\|不合格} — {1行要約}` ＋ **`種別: 計画\|実装`** ＋観点／注意点（書式は `ticket-evaluate` の `journal-format.md`）。**status / done_ratio は変えない**。計画＝着手前可／実装＝原則レビュー中。不合格時は実装側へ差し戻しまたは着手禁止を促す |

**status_id / done_ratio は上記タイミングで必ず Redmine API 更新**（SKILL.md「Redmine 更新」）。省略禁止。評価ノートだけは status を触らない例外。

中間の `notes` 連投（進捗報告コメント）は不要。詰まったときだけ追記してよい。

## 分割証拠（HARD GATE 用）

着手前に、対象チケット（分割した場合は親）の **Redmine journals** に次のいずれかが **実在**すること。チャット上の「判定した」だけでは不可。

書き込みは Redmine の **ジャーナル（`notes`）** のみ。手順の最短例は `ops.md`。

### 証拠にならないもの（禁止）

次を分割証拠の代わりにしてはならない。あっても親ジャーナルに `分割:` / `分割不要:` が無ければ HARD GATE 未充足:

- 子チケットの `parent_issue_id`（親子ツリー）だけ
- チャット／思考ログ上の「分割した」「分割不要と判断した」
- リポジトリ内のローカルメモ（例: `.redmine/.../journal_notes.md`）や未 push の下書き
- 「ツールが無い」を理由にしたスキップ（`redmine_issues` の `action: "update"` + `notes` で書ける）

### `分割:`（子を作ったとき）

```
分割: 機能構成→セッション完走
- #{子1}: {タイトル1}
- #{子2}: {タイトル2}
作業単位は子。親はハブ。
```

### `分割不要:`（子を作らないとき・省略禁止）

1行で次をすべて含める:

```
分割不要: DoD={n}個 / 中心ファイル目安={少数|1成果} / 理由={1セッションで着手〜Resolvedまで収まる根拠}
```

**禁止**: 機械的必須分割（`ticket-split` の policy: 必須トリガ A–G。DoD≥4 / 独立塊≥2 / 中心成果≥2 / 中心パス≥4 / 同居禁止 / 改修入口≥2 等。事前に数える指標のみ）に該当する親で `分割不要:` を書くこと。該当なら子を作れ。

**禁止**: `分割不要: 単一まとまり` のような理由なし／短い言い逃れ。

## 委任パック（着手時）

`着手:` ノートには `delegate-pack.md` の6項目を含める。欠落した着手は HARD GATE 未充足（実装に入らない）。

## 決定事項の転記

評価・設計判断・ユーザー指示を description や別の票の notes へ反映するときは、**要約せずに原文を引用**する。会話が長くなると、前の決定を記憶から言い換えたときに意味が反転しやすい。

```
> {原文の該当文}
（出典: #{id} journal #{journal_id}）
```

- 引用の前後に自分の解釈を足すのはよいが、引用部分は書き換えない
- **向きを持つ記述**（する／しない、付ける／付けない、有／無、許可／拒否、空／非空、含む／除く など）を転記・言い換えた場合は、反映後に原文と突き合わせ、次の1行を残す:

```
転記確認: #{id} journal #{journal_id} と一致
```

- 突き合わせで食い違いが見つかったら、反映先を直してから先へ進む（「後で直す」にしない）

## 判断の記録

DoD・着手・完了ノートには「何をしたか」は残るが、「なぜそうしたか」は残らない。理由が無いと、前提が変わったときに見直すべき判断か分からず、やめた案を次の作業者がまた試し、残した設定を外してよいかも判断できない。設計上の選択をしたら、その理由を Redmine に残す。

**書く条件（いずれか1つに当たるとき）:**

1. **他の案があった** — 検討して採らなかった方式・ツール・構成がある
2. **数値・パラメータ・方式を選んだ** — 上限値、サイズ、タイムアウト、既定値、採用するライブラリなど、別の値・別の方式もありえたもの
3. **作業途中で方針を変えた** — 実測が予想と違った、ユーザーに訂正された、計画どおりに進められなかった

**書かない条件:** 上のどれにも当たらない票（要件がそのまま実装を決めている、選択の余地が無い）では書かない。「理由: 要件どおり」「理由: 一般的なため」のような定型文で埋めることは **禁止**（定型文は読み飛ばされ、本当の判断が埋もれる）。

**書く場所:**

- 起票・精緻化の時点で決めたこと → description の `## 判断` 節（`ticket-refine` のテンプレ）
- 着手後に決めたこと・変えたこと → ジャーナルの `判断:`（下記書式）。description の判断を覆した場合も `判断:` を書き、description の `## 判断` を直す（覆した旧判断は削らず「→ journal #{id} で変更」と残す）

**書式:**

```
判断: {決めたこと（1行）}
- 理由: {根拠。実測値・ログ・ユーザー指示・ドキュメントを引用する}
- 却下: {検討してやめた案} — {やめた理由}（無ければ行ごと省略）
- 前提: {これが変わったら見直す条件}
```

- **理由** は根拠を引用する。「速いから」ではなく「実測で 10 万トークン超から生成速度が半減した（`{ログ／コマンド}`）」のように、後から確かめられる形で書く。ユーザー指示なら原文を引用する（上記「決定事項の転記」）
- **却下** は、次の作業者が同じ案を再試行しないためにある。やめた理由が「試して駄目だった」なら、その結果も書く
- **前提** は見直しのきっかけになる。モデル・バージョン・負荷・利用者数など、変わりうる条件を名指しする
- 1つの `判断:` に1つの決定。複数あるなら分けて書く

## 完了ノートとクローズ監査

`完了:` の前に `close-audit.md` を満たす。`検証:` 欄の証跡の種類（`実行`／`ログ`／`添付`／`目視`）は `close-audit.md`「検証証跡」。形式:

```
完了: {概要}
検証:
- [x] {DoD項目1} — 実行: `{コマンド}` → {n} pass / {m} fail
- [x] {DoD項目2} — 添付: {ファイル名}
- [ ] {DoD項目3} — 未実行: {理由}
判断参照: journal #{journal_id} / description「判断」（該当するときだけ。上記「判断の記録」の書く条件に当たらない票では行ごと省略）
クローズ監査: DoD全[x]=yes / 検証一致=yes / 親実装なし=yes / 範囲内=yes / 調査のみでない=yes / ステータス実体=yes / done_ratio実体=yes / 人手想定とブースト=yes / 評価済み=yes
ブースト: 想定{estimated_hours}h / 経過{h}h ≈ {倍率}x
```

予定・想定を実行済みとして書かない。`未実行:` が残る、または証跡の無い DoD 項目があるうちは監査項目2（検証一致）が no。監査が no の項目があるうちは **Resolved にしない**。status / done_ratio / `estimated_hours` はノートだけでなく `get` で確認（`close-audit.md` / `ops.md`）。進行中から直解決しない（レビュー＋評価済みが前提）。
