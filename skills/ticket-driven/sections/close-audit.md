# クローズ監査（Resolved 前必須）

`status_id` を Resolved（または同等の完了）にする **直前**に実施する。未充足なら完了ノートも Resolved も出さない。

## 前提（レビューフロー）

実装チケットは **進行中のまま解決しない**。順序は次のとおり（詳細は SKILL.md の D–F）:

1. 実装検証後 → **レビュー**（目安 status_id=7。`redmine_metadata` で確認）
2. `ticket-evaluate` が `評価:` を notes のみで書く（評価側は status を変えない）
3. **不合格** → レビュー→進行中に差し戻し（Resolved 禁止）
4. **合格 / 条件付き合格（ブロッカーなし）** → 本監査 → レビュー→解決

## 監査項目（すべて yes 必須）

| # | 項目 | yes の条件 |
|---|------|------------|
| 1 | DoD 全 `[x]` | description の完了条件がすべてチェック済み（未チェックが1つでもあれば no） |
| 2 | 検証一致 | 完了ノートの `検証:` 欄で、完了条件（DoD）の **各項目に証跡行が1つ以上**あり、テスト範囲・委任パックの「検証」と対応する（下記「検証証跡」）。証跡の無い項目・`未実行:` の項目・予定や想定だけの項目が1つでもあれば **no** |
| 3 | 親実装なし | 子がある親に実装差分・親 In Progress・親だけの「完了」で逃げていない |
| 4 | 範囲内 | 変更が影響範囲／委任パックの中心に収まる。DoD 外の追加成果を勝手に含めていない |
| 5 | 調査のみでない | DoD が現象解消／テスト pass なのに、調査メモだけで Resolved・新規戻ししていない。失敗アサーションを弱体化して「通った」扱いしていない |
| 6 | ステータス実体 | **完了ノートだけでは不足**。Resolved にする直前／直後の `get` で `status` が解決(3)（または同等の完了）であることを確認。終了(5)への遷移はエージェント通常経路では no。解決直前の状態は **レビュー** であること（進行中から直解決は no） |
| 7 | done_ratio 実体 | 進捗を扱う票では、解決前または同時に意図した `done_ratio`（多くは 100）が入っていることを `get` で確認。解決後に rate だけ直そうとして失敗したままなら no |
| 8 | 人手想定とブースト | 実装チケットで `estimated_hours`（人手想定）が入り、完了ノートに `ブースト:` 行がある。未設定のまま Resolved は no |
| 9 | 評価済み | journals に `評価: 合格` または `評価: 条件付き合格`（ブロッカーなし）がある。`評価: 不合格` のみ／評価ノート無しは no |

UI 変更がある場合は、既存の `ui-verify.md`（スクショ等）も満たすこと。

## 検証証跡（完了ノートの `検証:` 欄）

自己申告の「通った」「green」ではなく、**照合できる証跡**を DoD の項目ごとに書く。

| 種類 | 書くこと | 使える場面 |
|------|----------|------------|
| `実行` | 実行したコマンド（またはテスト名）と結果要約（pass/fail 件数・終了コード・主要出力） | テスト・ビルド・スクリプト・API 呼び出し |
| `ログ` | 実行ログの抜粋と取得場所（ファイル・ジョブ・ホスト） | デプロイ・バッチ・長時間ジョブ |
| `添付` | チケット添付のファイル名（スクショ・出力ファイル） | UI（`ui-verify.md`）・帳票・画面 |
| `目視` | 何を・どこで見たか（ファイルと節、画面と状態） | **実行手段が無い票のみ**（ドキュメントのみ・読み取り調査のみ） |

- 実行していない検証は **`未実行: {理由}`** と書く。予定・想定・「計画どおり」を実行済みとして書くことは **禁止**
- 1つの証跡で複数の DoD を覆ってよい。そのときは覆う項目それぞれの行に同じ証跡を書く（または「DoD 1〜2 — 実行: …」と範囲を明記）
- 証跡は **この票の作業中に** 得たものに限る。過去の実行結果・他票の結果の流用はしない

## 完了ノート形式

```
完了: {概要}
検証:
- [x] {DoD項目1} — 実行: `{コマンド}` → {n} pass / {m} fail
- [x] {DoD項目2} — 添付: {ファイル名}
- [ ] {DoD項目3} — 未実行: {理由}
クローズ監査: DoD全[x]=yes / 検証一致=yes / 親実装なし=yes / 範囲内=yes / 調査のみでない=yes / ステータス実体=yes / done_ratio実体=yes / 人手想定とブースト=yes / 評価済み=yes
ブースト: 想定{estimated_hours}h / 経過{h}h ≈ {倍率}x
```

`ブースト:` の計算は `ops.md`「人手想定とブースト」。どれか1つでも `no` → **Resolved 禁止**。不足を直すか、範囲外は別票へ切る。

## 親ハブの Resolved

全子が Resolved のあとだけ。親のクローズ監査は次を見る:

- 子がすべて Resolved
- 親 description の完了条件を子で充足した旨が追跡できる（`done_ratio` 100 または完了ノートで子 ID 列挙）。親も **Open 中に rate を入れてから** 解決(3)
- 親に実装を載せていない

## チェック

- [ ] 監査9項目がすべて yes（評価済み含む）
- [ ] 完了ノートの `検証:` 欄で、DoD の全項目に証跡行がある（`未実行:` が残っていない）
- [ ] 完了ノートに `クローズ監査:` 行と `ブースト:` 行がある
- [ ] 解決直前の status がレビューだったことを journals / get で確認した
- [ ] `get` で status / done_ratio / `estimated_hours` を確認したあと Resolved（終了5は使わない）
