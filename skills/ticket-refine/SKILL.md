# チケット精緻化 (Ticket Refinement)

曖昧な Redmine チケットを、実装可能な状態に整える。

## 自動起動（ticket-driven から）

`ticket-driven` の着手・実装フローで、完了条件が検証不能なときは **ユーザー確認なしで本スキルを実行**する。

1. 最小テンプレ／DoD 補完で description を更新
2. ジャーナル `精緻化: {要約}`
3. 呼び出し元へ戻し、**実装の前に `ticket-split`（機能構成単位）へ進む**（許可待ちしない）

まだ DoD が書けない場合だけ質問を最大3つ。推測で埋められる範囲は埋めて進める。

精緻化不要（DoD が既に検証可能）でも、呼び出し元は **同じタイミングで `ticket-split` を判定**する。本スキルをスキップしたからといって分割判定までスキップしない。

## 精緻化する／しない

| する（自動 or 明示） | しない |
|------|--------|
| 着手時に完了条件が検証不能（「良くする」「対応する」だけ） | 検証可能な完了条件が既にある（説明が短くても可） |
| 範囲が不明で影響ファイルの見当がつかない | 質問・設計相談のみ |
| ユーザーが `#N 精緻化` と明示 | |

精緻化のゴールは長文化ではない。**実装を始められる完了条件**を作ること。

精緻化の直後（または精緻化不要判定の直後）は、必ず `ticket-split` で **機能構成単位**に分解してから作業する。無理に1枚の親へ実装を詰め込まない。単一機能構成なら split 側が「分割不要」と判定する。

## 登録先プロジェクト（誤り防止）

精緻化対象チケットの **所属プロジェクトを変えたり、別プロジェクトへ新規を切ったりしない**。

- アプリ固有（例: brave-search-mcp）→ そのプロジェクトのチケットを更新
- スキル／運用ルール本体（ticket-driven）→ `{your-redmine-project}`
- ワークスペースのカレントだけでプロジェクトを推測しない。`get` の `project` を見る

## 最小フロー（デフォルト）

1. `get`（`include: ["journals"]`）
2. 欠けているのは主に「検証可能な完了条件」か？ → それだけ足して更新してよい
3. 必要なら最小テンプレで description を差し替え
4. ジャーナル: `精緻化: {要約}`

リモート未確保で実装不能なら、コメントに「リポジトリ未作成」→ Feedback 等で保留（毎回必須検査ではない。実装チケットで remote が要るときだけ）。

### get / update

取得（`redmine_issues`）:

```json
{ "action": "get", "issue_id": "{ID}", "include": ["journals"] }
```

説明更新 + ノート（`redmine_api_request`。`redmine_issues` に update/add_note は無い）:

```json
{
  "method": "PUT",
  "path": "/issues/{ID}.json",
  "body": {
    "issue": {
      "description": "{精緻化内容}",
      "notes": "精緻化: {要約}"
    }
  }
}
```

## 完了条件（最重要）

悪い例（禁止に近い）:

- 品質を高める / 適切に対応する / 堅牢にする
- 必要に応じてテストする

良い例:

- `cargo test` が通る
- `src/brave_search.rs` に 429 リトライ（最大3回）が入る
- README の「テスト / CI」にモック手順が1段落ある
- `scripts/ci.sh` が exit 0

書けない完了条件は、質問を **最大3つ** に絞ってユーザーへ返す（質問リストの量産はしない）。

## 最小テンプレ（デフォルトで使う）

```
## 背景
（1〜3文）

## 目的
（このチケットで達成すること・1〜2文）

## 完了条件
- [ ] 検証可能な条件1
- [ ] 検証可能な条件2

## 影響範囲
- 変更予定: path/to/file（分かれば）

## 実装方針
（任意・分かれば箇条書き1〜3）
```

非機能・エッジケース・詳細要件は、**完了条件を書くために必要なときだけ**足す。毎回フル項目を埋めない。

## 拡張チェック（不足が明らかなときだけ）

| 項目 | 見るポイント |
|------|----------------|
| 概要 | 何がどうなるか一言で言えるか |
| 完了条件 | コマンド／差分で判定できるか |
| 影響範囲 | 触るファイル・モジュールの見当 |
| 依存 | 他チケット・外部サービス待ちがあるか |

質問を出す場合の観点（必要なものだけ）:

- 入力／出力の形
- 失敗時の期待（エラーメッセージ、リトライ有無）
- テストの有無（単体 / 無視付き結合）

## 精緻化後チェック

- [ ] 完了条件がすべて検証可能
- [ ] 次工程の `ticket-split`（機能構成単位）へ渡せる状態である
- [ ] 正しいプロジェクトのチケットを更新した
- [ ] ジャーナルに精緻化要約がある

## 例

### 前

```
リトライを入れたい
```

### 後

```
## 背景
Brave API の一時的な 429/5xx でツール呼び出しが即失敗する。

## 目的
一時障害時に限って安全にリトライする。

## 完了条件
- [ ] 429 と 5xx と接続エラーのみリトライ（401/403 はしない）
- [ ] 最大3回・指数バックオフ
- [ ] ユニットまたはモックテストでリトライ経路を1つ以上検証
- [ ] `cargo test` が通る

## 影響範囲
- 変更: src/brave_search.rs
```
