# 充足チェック・テスト合格ライン・完了条件

## 充足チェック（分割前）

次をすべて満たせば更新スキップ。1つでも欠けたら埋める。見出し名は一致しなくてよい（同等の内容があれば可）。

| 項目 | 見るポイント |
|------|----------------|
| 命題のリッチ化 | 題名の言い換えで終わっていないか。達成状態と実現の内訳があるか |
| 品質観点 | 該当軸の問いを通し、抽象語が検証可能な条件／テストに落ちているか |
| 背景・目的 | 何がどうなるか一言で言えるか（リッチ化後の1文と一致） |
| 範囲 | やる／やらないが、命題と品質観点から導かれているか |
| 完了条件 | コマンド／差分／操作で判定できるか（品質観点由来の条件を含む） |
| 分割候補 | 下記「分割候補リスト」を満たすか（無いと split がスキップされやすい） |
| 影響範囲 | 触るファイル・モジュールの見当 |
| テスト範囲 | 下記の合格ラインを満たすか（見出しがあるだけでは不可） |
| 失敗時・境界 | 振る舞いが自明でないとき、期待が書いてあるか |
| 依存 | 他チケット・外部サービス待ちがあるか（無ければ「なし」で可） |

### 分割候補リスト（必須）

description のどこかに、次のいずれかがあること（見出し名は自由）:

- **候補が2行以上**: 能力／検証可能なまとまりを箇条書き（例: CORS 修正 / preflight 経路 / handshake 検証）。親 DoD を全部1塊にしない
- **単一理由1行**: `分割候補: 単一 — {子の合格ライン根拠}`（DoD 1〜3・中心成果1・同居なし。壁時計は書かない）

親の完了条件を4個以上並べるだけ、で分割候補が無い → **不足**（更新する）。実際の分割は直後の `ticket-split`（必須トリガ A–F は `ticket-split` の `policy.md`）。

失敗時・境界は、バグの再現手順や「〜しない」が完了条件に既にあるなら追加しない。

非機能・エッジケースは **分割と実装に必要なときだけ**足す。毎回フル項目を埋めない。

命題が薄い → 先に `proposition.md`。観点の落とし方 → `quality-axes.md`。

## テスト範囲の合格ライン

正本はここ。着手後に別の計画を書き足さない（漏れ拾いは `ticket-driven`）。

必須:

- **完了条件との対応**: 各完了条件について、どう検証するかを書く。1コマンドで複数をまとめてよいが、どれを見るかは書く
- **手段の区別**: 各項目を 自動 / 手動 / 目視 のいずれかにする
- **失敗経路**: 範囲に失敗時・境界があるなら、その経路を1つ入れる

不合格（これだけでは足りない）:

- DoD の言い換えだけでは不合格
- `cargo test` が通る、だけ（完了条件の言い換え）
- 対象・手順・合格の見出しだけ埋まって、中身が完了条件のコピー
- 網羅表・カバレッジ目標（要求しない）

例外: ドキュメントのみ・読み取り調査のみは「目視確認」で計画扱いしてよい。

**UI・画面・見た目の変更**では追加で必須:

- Playwright（または同等のブラウザ自動）で意図どおりかを確認する手順
- スクリーンショットをチケットに添付する（手段は `./tools/redmine_helper.sh attach`。MCP ではバイナリ不可）

分割後は **子が自分の完了条件に対応した計画** を持つ。親の薄いテスト範囲をコピーしない。

## 完了条件（必須）

悪い例（禁止に近い）:

- 品質を高める / 適切に対応する / 堅牢にする
- 必要に応じてテストする
- 使いやすい / メンテしやすい（品質観点の抽象語）

良い例:

- `cargo test` が通る
- `src/brave_search.rs` に 429 リトライ（最大3回）が入る
- README の「テスト / CI」にモック手順が1段落ある
- `scripts/ci.sh` が exit 0
- リトライ判定を純関数に切り出し、モックで 429/401 をユニット検証できる

書けない完了条件は、質問を **最大3つ** に絞ってユーザーへ返す。

質問を出す場合の観点（必要なものだけ）:

- 入力／出力の形
- 失敗時の期待（エラーメッセージ、リトライ有無）
- テストの有無（単体 / 無視付き結合）

## 精緻化後チェック

- [ ] 命題が達成状態・実現の内訳まで展開されている
- [ ] 該当する品質観点が、完了条件またはテストに落ちている
- [ ] 充足チェックをすべて満たす（**分割候補リスト**を含む）
- [ ] テスト範囲が合格ラインを満たす（DoD の言い換えだけではない）
- [ ] 完了条件がすべて検証可能
- [ ] 次工程の `ticket-split`（機能構成→セッション完走）へ渡せる状態である
- [ ] 正しいプロジェクトのチケットを更新した（または更新スキップした）
- [ ] ジャーナルに精緻化要約がある
