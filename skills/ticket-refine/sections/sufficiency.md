# 充足チェック・テスト合格ライン・完了条件

## 充足チェック（分割前）

次をすべて満たせば更新スキップ。1つでも欠けたら埋める。見出し名は一致しなくてよい（同等の内容があれば可）。

| 項目 | 見るポイント |
|------|----------------|
| 命題のリッチ化 | 題名の言い換えで終わっていないか。達成状態と実現の内訳があるか |
| 品質観点 | 該当軸の問いを通し、抽象語が検証可能な条件／テストに落ちているか |
| 背景・目的 | 何がどうなるか一言で言えるか（リッチ化後の1文と一致） |
| 範囲 | やる／やらないが、命題と品質観点から導かれているか |
| **既存入口の処分** | **既存能力の改修**なら、現状の入口一覧と各入口の処分（`改修`／`据え置き`＋理由／`廃止`／`移行`）があるか。一覧なし・処分なし・黙殺は **不足**。**greenfield・ドキュメントのみ・調査のみは不要**（非適用と分かればスキップ可） |
| **判断の根拠** | 設計上の選択（他の案があった／数値・パラメータ・方式を選んだ）があるなら、`## 判断` に決定・理由・却下・前提があるか（書式は `ticket-driven` の `sections/journal.md`「判断の記録」）。理由が定型文（「要件どおり」「一般的なため」）なら **不足**。旧本文にあった根拠が更新後に消えていたら **不足**（下記「根拠を削らない」）。**選択の余地が無い票は不要**（`## 判断` ごと省略してよい） |
| 完了条件 | コマンド／差分／操作で判定できるか（品質観点由来の条件を含む） |
| 分割候補 | 下記「分割候補リスト」を満たすか（無いと split がスキップされやすい） |
| 影響範囲 | 触るファイル・モジュールの見当 |
| テスト範囲 | 下記の合格ラインを満たすか（見出しがあるだけでは不可） |
| 失敗時・境界 | 振る舞いが自明でないとき、期待が書いてあるか |
| 依存 | 他チケット・外部サービス待ちがあるか（無ければ「なし」で可） |
| 人手想定 | 実装チケット（この時点で単一票／後の子になる親）で `estimated_hours` が人手想定として入っているか。null なら update で埋める。エージェント前提の短縮見積は不可（`ticket-driven` / `ticket-create` fields） |

### 分割候補リスト（必須）

description のどこかに、次のいずれかがあること（見出し名は自由）:

- **候補が2行以上**: 能力／検証可能なまとまりを箇条書き（例: CORS 修正 / preflight 経路 / handshake 検証）。親 DoD を全部1塊にしない
- **単一理由1行**: `分割候補: 単一 — {子の合格ライン根拠}`（DoD 1〜3・中心成果1・同居なし。壁時計は書かない）

親の完了条件を4個以上並べるだけ、で分割候補が無い → **不足**（更新する）。実際の分割は直後の `ticket-split`（必須トリガ A–G は `ticket-split` の `policy.md`）。

失敗時・境界は、バグの再現手順や「〜しない」が完了条件に既にあるなら追加しない。

非機能・エッジケースは **分割と実装に必要なときだけ**足す。毎回フル項目を埋めない。

命題が薄い → 先に `proposition.md`。観点の落とし方 → `quality-axes.md`。

## 根拠を削らない（description 更新時）

精緻化は本文を整える作業なので、実測値・ユーザー指示・やめた案の理由が「冗長」に見えて削られやすい。削られた根拠は変更履歴の差分にしか残らず、後から読む人には見えない。

- description を書き換える前に、旧本文から **根拠**（実測値・ログ・ユーザー指示・却下した案とその理由・前提条件）を拾う
- 根拠は **削除禁止**。`## 背景` か `## 判断` へ **移すことだけ** 許す。言い換えるときは「決定事項の転記」（`ticket-driven` の `sections/journal.md`）に従い原文を引用する
- 根拠が誤りと分かった場合も消さない。「→ 実測で否定（journal #{id}）」のように注記し、新しい根拠を併記する
- 起票直後の精緻化で根拠がまだ無い票（選択の余地が無い票）は対象外

## テスト範囲の合格ライン

正本はここ。着手後に別の計画を書き足さない（漏れ拾いは `ticket-driven`）。

必須:

- **完了条件との対応**: 各完了条件について、どう検証するかを書く。1コマンドで複数をまとめてよいが、どれを見るかは書く
- **手段の区別**: 各項目を 自動 / 手動 / 目視 のいずれかにする
- **検証の強さ**: 各完了条件が求める振る舞いの段階に届く検証を選ぶ（下記「検証の強さ」）
- **失敗経路**: 範囲に失敗時・境界があるなら、その経路を1つ入れる

不合格（これだけでは足りない）:

- DoD の言い換えだけでは不合格
- `cargo test` が通る、だけ（完了条件の言い換え）
- 対象・手順・合格の見出しだけ埋まって、中身が完了条件のコピー
- 完了条件が求める段階より弱い検証だけ（下記「検証の強さ」）
- 網羅表・カバレッジ目標（要求しない）

例外: ドキュメントのみ・読み取り調査のみは「目視確認」で計画扱いしてよい。

**UI・画面・見た目の変更**では追加で必須:

- Playwright（または同等のブラウザ自動）で意図どおりかを確認する手順
- スクリーンショットをチケットに添付する（手段は `./tools/redmine_helper.sh attach`。MCP ではバイナリ不可）

分割後は **子が自分の完了条件に対応した計画** を持つ。親の薄いテスト範囲をコピーしない。

### 検証の強さ

検証は次の段階で強くなる。完了条件が求める段階 **より弱い検証** は、その完了条件のテスト範囲として **不合格**。

| 段階 | 確かめるもの | 例 |
|------|--------------|----|
| 静的確認 | ファイル内容・文字列・型・設定値が書かれていること | 定義ファイルに制約名が含まれる、型チェックが通る |
| 単体 | 1つの関数・モジュールの入出力 | 純関数の境界値、モックした依存での分岐 |
| 結合 | 実際の依存（DB・プロセス・ファイル・ネットワーク）と組んだ振る舞い | 実 DB への重複登録が拒否される、API がその応答を返す |
| 実環境 | 本番相当の環境・データ・手順での振る舞い | デプロイ後に件数が変わらない、運用手順どおりに復旧できる |

- 完了条件が「〜が拒否される」「〜が両立する」のように **実行時の振る舞い** を言っているなら、静的確認だけでは足りない（例: 一意制約が DoD なら、定義の文字列確認ではなく、実 DB への重複登録が拒否されることを確かめる）
- 「実物」が要るのは **DoD の対象そのもの** だけ。DoD の対象（例: DB への反映）を実物で確かめていれば、DoD が名指ししていない外部サービス（例: 認証基盤・外部 API）はテスト用の代理（モック・スタブ）でも結合とみなす。外部サービス自体の実挙動が DoD に書かれているときだけ、その外部サービスの実物（実環境）が要る
- 実環境の検証が別の子（デプロイ票など）に分かれているなら、この票は結合までを書き、実環境はその子のテスト範囲に置く
- ドキュメントのみ・読み取り調査のみは、従来どおり「目視確認」でよい（上記例外）

## 完了条件（必須）

悪い例（禁止に近い）:

- 品質を高める / 適切に対応する / 堅牢にする
- 必要に応じてテストする
- 使いやすい / メンテしやすい（品質観点の抽象語）

良い例:

- `cargo test` が通る
- `src/brave_search.rs` に 429 リトライ（最大3回）が入る
- README の「テスト / CI」にモック手順が1段落ある
- `scripts/ci.sh` が exit 0
- リトライ判定を純関数に切り出し、モックで 429/401 をユニット検証できる

書けない完了条件は、質問を **最大3つ** に絞ってユーザーへ返す。

質問を出す場合の観点（必要なものだけ）:

- 入力／出力の形
- 失敗時の期待（エラーメッセージ、リトライ有無）
- テストの有無（単体 / 無視付き結合）

## 精緻化後チェック

- [ ] 命題が達成状態・実現の内訳まで展開されている
- [ ] 既存能力の改修なら、既存入口一覧＋各入口の処分がある（greenfield 等は非適用で可）
- [ ] 設計上の選択があるなら、`## 判断` に決定・理由・却下・前提がある（選択の余地が無い票は非適用で可）
- [ ] 旧本文にあった根拠（実測・ユーザー指示・却下理由・前提）を削っていない（移した場合は移動先にある）
- [ ] 該当する品質観点が、完了条件またはテストに落ちている
- [ ] 充足チェックをすべて満たす（**分割候補リスト**を含む）
- [ ] テスト範囲が合格ラインを満たす（DoD の言い換えだけではない。各完了条件が求める段階に届く検証の強さ）
- [ ] 完了条件がすべて検証可能
- [ ] 次工程の `ticket-split`（機能構成→セッション完走）へ渡せる状態である
- [ ] 正しいプロジェクトのチケットを更新した（または更新スキップした）
- [ ] ジャーナルに精緻化要約がある
