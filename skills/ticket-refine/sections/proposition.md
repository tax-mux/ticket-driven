# 命題のリッチ化

題名・1行要望・薄い説明を、**このチケットで実現すべき内容**へ展開する。  
テンプレ見出しを足すだけ、DoD を検証可能にするだけでは不合格。

## 手順

1. **命題を1文で言い直す**（誰が／何が／どうなるか）
2. **達成状態を具体化する**（利用者または呼び出し側から見える変化）
3. **実現の内訳を列挙する**（能力・画面・API・データ・ドキュメント・運用手順など、該当するものだけ）
4. **既存能力の改修なら、既存入口を列挙し各入口の処分を決める**（下記。greenfield はスキップ）
5. **やる／やらないの境界**を命題から導く（推測で埋めてよい。確信が無いときだけ質問。据え置き・廃止しない入口は「やらない」に理由付きで残す）
6. 呼び出し元の概要に戻り、品質観点 → 充足チェックへ進む

### 既存入口の列挙と処分（既存能力の改修時のみ・必須）

**適用:** すでに利用者／呼び出し側から到達できる入口がある能力を変える・置き換える・一部移す票。  
**非適用（必須にしない）:** 新規能力の greenfield、ドキュメントのみ、調査のみ。

1. **現状の入口を列挙する**（URL・画面・API・CLI・バッチ・設定面など、その能力に触れるもの。プロダクト固有の固定リストは持たない）
2. **各入口に処分を1つ付ける:** `改修` / `据え置き`（理由1行） / `廃止` / `移行`
3. description のどこかに表または同等の箇条書きで残す（見出し名は自由。例: `既存入口`）

**禁止:** 新経路・主経路だけ書いて、並行する既存入口を黙殺する（据え置きなら理由を書く。沈黙は不合格）。

処分が `改修` の入口は、直後の `ticket-split` の独立塊／中心パスの入力になる（数え方は `ticket-split` の `policy.md`）。

## 不合格（リッチ化不足）

- 題名の言い換え＋`cargo test` だけ
- 「適切に実装する」「既存方針に従う」など中身の無い方針
- 実現の内訳が無く、分割しても子が「後半」「その他」になる
- 既存能力の改修なのに既存入口一覧または入口ごとの処分が無い（黙殺）

## 合格の目安

- 命題を読んだ第三者が、**何が出来上がるか**を同じ絵で説明できる
- 内訳が **機能構成の候補**（`ticket-split` 第1段）に使える粒度になっている
- 抽象語（使いやすい／堅牢／綺麗）が、検証可能な条件に落ちる手前まで具体化されている
- 既存改修なら、第三者が「触らない入口」と「触る入口」を処分表から同じ絵で言える

次が必要なら:

- 成果物・UI → `quality-axes.md`
- 充足・テスト合格ライン → `sufficiency.md`
- テンプレ・例 → `template-examples.md`
