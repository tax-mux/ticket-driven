# 命題のリッチ化

題名・1行要望・薄い説明を、**このチケットで実現すべき内容**へ展開する。  
テンプレ見出しを足すだけ、DoD を検証可能にするだけでは不合格。

## 手順

1. **命題を1文で言い直す**（誰が／何が／どうなるか）
2. **達成状態を具体化する**（利用者または呼び出し側から見える変化）
3. **実現の内訳を列挙する**（能力・画面・API・データ・ドキュメント・運用手順など、該当するものだけ）
4. **やる／やらないの境界**を命題から導く（推測で埋めてよい。確信が無いときだけ質問）
5. 呼び出し元の概要に戻り、品質観点 → 充足チェックへ進む

## 不合格（リッチ化不足）

- 題名の言い換え＋`cargo test` だけ
- 「適切に実装する」「既存方針に従う」など中身の無い方針
- 実現の内訳が無く、分割しても子が「後半」「その他」になる

## 合格の目安

- 命題を読んだ第三者が、**何が出来上がるか**を同じ絵で説明できる
- 内訳が **機能構成の候補**（`ticket-split` 第1段）に使える粒度になっている
- 抽象語（使いやすい／堅牢／綺麗）が、検証可能な条件に落ちる手前まで具体化されている

次が必要なら:

- 成果物・UI → `quality-axes.md`
- 充足・テスト合格ライン → `sufficiency.md`
- テンプレ・例 → `template-examples.md`
