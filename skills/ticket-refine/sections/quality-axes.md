# 品質観点

リッチ化した実現内容に対し、該当する軸だけ検討する。  
毎回4軸フル作文はしない。結果は **範囲・完了条件・テスト** に落とす（「検討した」だけの節を増やさない）。

| 観点 | 問い | 落とす先の例 |
|------|------|----------------|
| 利用しやすさ | 成果物の入り口は短いか。既定値・手順・ドキュメントで迷わないか | README の手順1本、デフォルトで動く、エラーが次の一手を示す |
| 改造しやすさ | 次の変更はどこに足すか分かるか。拡張点が1か所に寄っているか | 設定の単一入口、プラグイン境界、公開 API の安定面 |
| メンテしやすさ | 責務の切れ目は清いか。テストで回帰を止められるか。依存は太すぎないか | モジュール分割、テスト可能な境界、ログの要点 |
| UI使いやすさ | 主操作は短いか。初見で迷わないか。失敗時に回復できるか | 主経路の操作数、ラベル、空状態、エラー表示 |

## 必須／任意

| 条件 | 必須の観点 |
|------|------------|
| コード・設定・スキル・ライブラリ等の成果物 | 利用・改造・メンテ（該当する問いだけ） |
| 画面・操作・見た目・フロントの変更 | 上記＋ **UI使いやすさ** |
| ドキュメントのみ・文言のみ | 利用しやすさ（読み手が迷わないか）に絞ってよい |
| バグ修正で再現と修正が自明 | 回帰を止めるメンテ観点だけでも可 |

## 禁止

- 「使いやすい」「メンテしやすい」を完了条件に書く
- 観点名だけの見出しを本文に増やす（中身が条件／テストに落ちていない）
- ユーザー未指示の大規模リデザインを「使いやすさ」名目で足す

## 完了条件への落とし方（良い例）

- 利用: 「README の Quick start から、追加設定なしでサンプルが1コマンドで動く」
- 改造: 「新しい Provider は `providers/` に1ファイル足すだけで登録できる」
- メンテ: 「リトライ判定は純関数に切り出し、ユニットテストで 429/401 を固定する」
- UI: 「検索の主経路は一覧表示まで3操作以内。0件時は空状態メッセージを出す」

`## 品質観点` という見出しはチケット本文のテンプレに**入れない**（条件へ落とすため）。

次: 充足チェック・テストは `sufficiency.md`。例は `template-examples.md`。
