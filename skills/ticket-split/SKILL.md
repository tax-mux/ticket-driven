# チケット分割 (Ticket Splitting)

親チケットを **機能構成単位** の子チケットに分割し、作業を細分化する。

## 自動起動（ticket-driven から）

`ticket-driven` で精緻化が済んだ、または精緻化不要（DoD 検証可能）と判定された直後に、**ユーザー確認なしで本スキルを実行**する。

1. 親を `get` し、既存の子の有無を確認する
2. 機能構成単位で分割案を作る
3. 分割するなら子を作成し、依存を `ticket-relation` で付け、親に分割ジャーナルを書く
4. 呼び出し元へ戻し、**子チケットを作業単位**として実装へ進む（許可待ちしない）

すでに子がある／単一機能構成で分割不要 → 作成せず「分割不要」と判定して戻る。

## 目的

- 与えられたチケットを、実装可能な **機能構成** に分解する
- 各子が独立した完了条件を持ち、順に（または並列に）完走できるようにする
- 親は範囲のハブ（進捗・最終 Resolved）に留める

## 分割方針

### 主基準: 機能構成単位（必須）

機能構成とは、プロダクト上のまとまりとして説明できる単位。層やファイルの切れ目より、**ユーザー／システムが得る能力の境界**を優先する。

| 良い分割（機能構成） | 避けたい分割 |
|----------------------|--------------|
| 認証（ログイン／セッション） | 「フロント半分」「バック半分」だけの層切り |
| 一覧表示、詳細表示、編集 | ファイル1つずつの機械分割 |
| モデル＋永続化、公開 API、画面 | 「手順1」「手順2」だけの作業メモ分割 |
| コア実装、検証／テスト（構成が大きいとき） | 完了条件の箇条書きを1行＝1子にする機械分割 |

判定手順:

1. 親の目的・完了条件を読み、構成要素（能力・画面・API・データ・検証）を列挙する
2. 各要素が **独自の検証可能な完了条件** を持てるか見る
3. 持てる要素が **2つ以上** → 子チケット化する
4. 1つにしかならない → 分割しない（親のまま着手）

### 補助基準（主基準のあとで使う）

- **階層単位**: 同一機能構成の中で FE / BE / DB が独立に検証できるときだけ細分
- **ファイル単位**: 影響範囲が明確で、機能構成と一致するとき
- **ステップ単位**: 順序依存が強く、途中成果物が検証可能なとき

### 分割しない場合

- すでに機能構成が1つ（単一の検証可能なまとまり）
- 1回のコミットで完結する小さな変更
- 依存が強く、切り離すとどちらも完了条件を検証できない
- すでに子チケットがある（再分割しない。不足があれば親のジャーナルで追記案を残す）
- ユーザーが「分割するな」と明示

## ワークフロー

### 1. 分割計画

親チケットの内容を分析し、**機能構成**で分割案を策定:

```
## 分割案（機能構成単位）

### 子チケット1: {機能構成名}
- 内容: ...
- 完了条件: ...
- 依存: なし（先行）
- 推定工数: ...

### 子チケット2: {機能構成名}
- 内容: ...
- 完了条件: ...
- 依存: 子チケット1
- 推定工数: ...
```

### 2. 子チケット作成

```json
{
  "method": "POST",
  "path": "/issues.json",
  "body": {
    "issue": {
      "project_id": "{プロジェクトID}",
      "parent_issue_id": 42,
      "tracker_id": 2,
      "subject": "{機能構成のタイトル}",
      "description": "{説明}",
      "priority_id": 2
    }
  }
}
```
ツール: `redmine_api_request`（`redmine_issues` に create は無い）

親と **同じプロジェクト** に作る。プロジェクトを跨がない。

### 3. 関連付け

子同士の順序依存は `precedes` / `blocks` 等で明示（単なる `relates` だけにしない）:

```json
{
  "method": "POST",
  "path": "/issues/{先行ID}/relations.json",
  "body": {
    "relation": {
      "issue_to_id": 43,
      "relation_type": "precedes"
    }
  }
}
```
ツール: `redmine_api_request`

### 4. 親チケット更新

分割内容を親チケットのジャーナルに記録:

```json
{
  "method": "PUT",
  "path": "/issues/{親ID}.json",
  "body": {
    "issue": {
      "notes": "チケットを分割（機能構成単位）:\n- #{子1ID}: {タイトル1}\n- #{子2ID}: {タイトル2}"
    }
  }
}
```

分割しない場合:

```json
{
  "method": "PUT",
  "path": "/issues/{親ID}.json",
  "body": {
    "issue": { "notes": "分割不要: 単一の機能構成として着手" }
  }
}
```

（ジャーナルは分割実行時は必須。分割不要は親がまだ New のままなら省略可だが、判定した事実は呼び出し元フローで明示する。）

### 5. 親チケットの進捗

子チケットの完了率に応じて進捗率を更新:

```json
{
  "method": "PUT",
  "path": "/issues/{親ID}.json",
  "body": { "issue": { "done_ratio": 33 } }
}
```

全子 Resolved 後に親を Resolved する（`ticket-driven` 側）。

## 子チケット作成テンプレート

### Bug（修正系）

```
## 修正内容
{バグの説明}

## 修正方針
{どのように修正するか}

## 完了条件
- [ ] {具体的な検証条件}

## 影響確認
- [ ] 関連箇所の動作確認
- [ ] 回帰テスト
```

### Feature（実装系）

```
## 背景
{なぜ必要か}

## 実装内容
{この機能構成で何をするか}

## 実装詳細
### 変更ファイル
- {ファイルパス}: {変更内容}

### 新規ファイル
- {ファイルパス}: {用途}

## 完了条件
- [ ] {検証条件1}
- [ ] {検証条件2}

## テスト
- [ ] 単体テスト
- [ ] 結合テスト
```

### Task（作業系）

```
## 作業内容
{この機能構成の具体的な作業}

## 手順
1. {手順1}
2. {手順2}

## 完了条件
- [ ] {確認項目1}
- [ ] {確認項目2}
```

## 分割チェックリスト

- [ ] 分割軸が機能構成単位である（層・ファイル優先になっていない）
- [ ] 各子が独自の検証可能な完了条件を持つ
- [ ] 依存関係が明確（必要なら relation 済み）
- [ ] 親の範囲を網羅し、重複がない
- [ ] 親チケットに分割記録がある
- [ ] 実装は親ではなく子で着手する

## 例

### 親チケット: "ユーザー管理機能の実装"

分割後（機能構成単位）:

```
#{101} ユーザーモデル・永続化
  依存: なし（先行）
  内容: User モデル、バリデーション、スコープ

#{102} ユーザー CRUD API
  依存: #{101}
  内容: 一覧・詳細・作成・更新・削除 API

#{103} ユーザー一覧画面
  依存: #{102}
  内容: 一覧表示・検索・ページネーション

#{104} ユーザー詳細・編集画面
  依存: #{102}
  内容: 詳細表示・編集・削除

#{105} ユーザー管理の検証
  依存: #{101}, #{102}, #{103}, #{104}
  内容: 単体・結合で完了条件を担保
```
