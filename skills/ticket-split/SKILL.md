# チケット分割 (Ticket Splitting)

親チケットを **機能構成単位** の子チケットに分割し、作業を細分化する。

## 自動起動（ticket-driven から）

`ticket-driven` で精緻化が済んだ、または要件充足済み（更新スキップ）と判定された直後に、**ユーザー確認なしで本スキルを実行**する。

1. 親を `get` し、既存の子の有無を確認する
2. 機能構成単位で分割案を作る
3. 分割するなら子を作成する。**本文は親の切り出し**（プレースホルダ禁止）。依存を `ticket-relation` で付け、親に分割ジャーナルを書く
4. 呼び出し元へ戻し、**子チケットを作業単位**として実装へ進む（許可待ちしない）

すでに子がある／単一機能構成で分割不要 → 作成せず「分割不要」と判定して戻る。

## 目的

- 与えられたチケットを、実装可能な **機能構成** に分解する
- 各子は親の充足本文を **切り出した作業単位** であり、作成時点で `ticket-refine` と同じ充足ラインを満たす
- 親は範囲のハブ（進捗・最終 Resolved）に留める

## 子の本文は切り出し（プレースホルダ禁止）

親を精緻化したあと、子を薄いテンプレで作り直さない。**親の description を機能構成で切って配る。**

やる:

- この子が担う範囲・完了条件・影響範囲・テスト範囲だけを残す
- テスト範囲は **この子の完了条件** に対応させる（親の計画の丸コピー禁止）
- 失敗時・境界は、この子の振る舞いに必要なときだけ切って載せる
- 作成時点で `ticket-refine` の充足チェックとテスト範囲の合格ラインを満たす

やらない:

- `{なぜ必要か}` `{検証条件1}` のようなプレースホルダのまま作成する
- 親の本文を丸ごとコピーする
- 完了条件と「単体テスト」だけの薄い子を作り、着手時の精緻化に任せる

子の着手時の `ticket-refine` は **漏れ拾い**。split が充足していれば更新スキップ。

## 分割方針

### 主基準: 機能構成単位（必須）

機能構成とは、プロダクト上のまとまりとして説明できる単位。層やファイルの切れ目より、**ユーザー／システムが得る能力の境界**を優先する。

| 良い分割（機能構成） | 避けたい分割 |
|----------------------|--------------|
| 認証（ログイン／セッション） | 「フロント半分」「バック半分」だけの層切り |
| 一覧表示、詳細表示、編集 | ファイル1つずつの機械分割 |
| モデル＋永続化、公開 API、画面 | 「手順1」「手順2」だけの作業メモ分割 |
| コア実装、検証／テスト（構成が大きいとき） | 完了条件の箇条書きを1行＝1子にする機械分割 |

判定手順:

1. 親の目的・完了条件を読み、構成要素（能力・画面・API・データ・検証）を列挙する
2. 各要素が **独自の検証可能な完了条件** を持てるか見る
3. 持てる要素が **2つ以上** → 子チケット化する
4. 1つにしかならない → 分割しない（親のまま着手）

### 補助基準（主基準のあとで使う）

- **階層単位**: 同一機能構成の中で FE / BE / DB が独立に検証できるときだけ細分
- **ファイル単位**: 影響範囲が明確で、機能構成と一致するとき
- **ステップ単位**: 順序依存が強く、途中成果物が検証可能なとき

### 分割しない場合

- すでに機能構成が1つ（単一の検証可能なまとまり）
- 1回のコミットで完結する小さな変更
- 依存が強く、切り離すとどちらも完了条件を検証できない
- すでに子チケットがある（再分割しない。不足があれば親のジャーナルで追記案を残す）
- ユーザーが「分割するな」と明示

## ワークフロー

### 1. 分割計画

親チケットの内容を分析し、**機能構成**で分割案を策定:

```
## 分割案（機能構成単位）

### 子チケット1: {機能構成名}
- 範囲: やる / やらない（この子だけ）
- 完了条件: （この子だけ。検証可能）
- 影響範囲: ファイル・モジュール
- テスト範囲: この子の完了条件に対応。自動/手動/目視
- 依存: なし（先行）

### 子チケット2: {機能構成名}
- 範囲: …
- 完了条件: …
- 影響範囲: …
- テスト範囲: （親のをコピーしない）
- 依存: 子チケット1
```

### 2. 子チケット作成

```json
{
  "method": "POST",
  "path": "/issues.json",
  "body": {
    "issue": {
      "project_id": "{プロジェクトID}",
      "parent_issue_id": 42,
      "tracker_id": 2,
      "subject": "{機能構成のタイトル}",
      "description": "{説明}",
      "priority_id": 2
    }
  }
}
```
ツール: `redmine_api_request`（`redmine_issues` に create は無い）

`description` は下記テンプレを **埋めた本文**。プレースホルダや見出しだけの子は作らない。親と **同じプロジェクト** に作る。プロジェクトを跨がない。

### 3. 関連付け

子同士の順序依存は `precedes` / `blocks` 等で明示（単なる `relates` だけにしない）:

```json
{
  "method": "POST",
  "path": "/issues/{先行ID}/relations.json",
  "body": {
    "relation": {
      "issue_to_id": 43,
      "relation_type": "precedes"
    }
  }
}
```
ツール: `redmine_api_request`

### 4. 親チケット更新

分割内容を親チケットのジャーナルに記録:

```json
{
  "method": "PUT",
  "path": "/issues/{親ID}.json",
  "body": {
    "issue": {
      "notes": "チケットを分割（機能構成単位）:\n- #{子1ID}: {タイトル1}\n- #{子2ID}: {タイトル2}"
    }
  }
}
```

分割しない場合:

```json
{
  "method": "PUT",
  "path": "/issues/{親ID}.json",
  "body": {
    "issue": { "notes": "分割不要: 単一の機能構成として着手" }
  }
}
```

（ジャーナルは分割実行時は必須。分割不要は親がまだ New のままなら省略可だが、判定した事実は呼び出し元フローで明示する。）

### 5. 親チケットの進捗

子チケットの完了率に応じて進捗率を更新:

```json
{
  "method": "PUT",
  "path": "/issues/{親ID}.json",
  "body": { "issue": { "done_ratio": 33 } }
}
```

全子 Resolved 後に親を Resolved する（`ticket-driven` 側）。

## 子チケット作成テンプレート

充足項目は種別共通。空欄のまま作らない。合格ラインは `ticket-refine`。

### 共通（Feature / Task の本文）

```
## 背景
（親から、この機能構成に必要な1〜3文）

## 目的
（この子で達成すること）

## 範囲
- やる: （この子だけ）
- やらない: （親の他の子、またはこの子の外）

## 完了条件
- [ ] （この子で検証可能な条件）

## 影響範囲
- 変更: path/to/file

## テスト範囲
- 完了条件1: 自動 — {コマンド}（見るもの）
- 完了条件2: 手動または目視 — …
- 失敗経路: （この子の範囲に失敗時があるときだけ）
```

### Bug（修正系。共通に足す）

共通のうえに、再現・期待・実際を残す（親からこの不具合ぶんを切る）。範囲・影響範囲・テスト範囲は共通テンプレを使う。

```
## 再現手順
1. …

## 期待値
…

## 実際
…
```

回帰はテスト範囲に、完了条件との対応で書く（「回帰テスト」チェックだけにしない）。

### Task（作業系）

共通テンプレを使う。手順が必要なら「範囲」の下に書く。**テスト範囲を省略しない。**

## 分割チェックリスト

- [ ] 分割軸が機能構成単位である（層・ファイル優先になっていない）
- [ ] 各子が独自の検証可能な完了条件を持つ
- [ ] 各子が `ticket-refine` の充足ラインを満たす（範囲・影響範囲・テスト範囲。プレースホルダなし）
- [ ] 各子のテスト範囲が子の完了条件に対応している（親のコピーではない）
- [ ] 依存関係が明確（必要なら relation 済み）
- [ ] 親の範囲を網羅し、重複がない
- [ ] 親チケットに分割記録がある
- [ ] 実装は親ではなく子で着手する

## 例

### 親チケット: "ユーザー管理機能の実装"

親は精緻化済み（認証は範囲外、一覧と詳細は別構成、など）。分割後は切り出し:

```
#{101} ユーザーモデル・永続化
  依存: なし（先行）
  範囲: User モデル・バリデーション・永続化。API/画面は他の子
  完了条件: モデルが保存でき、必須項目のバリデーションが失敗する
  テスト範囲: 自動 — モデルの保存成功とバリデーション失敗を1つずつ

#{102} ユーザー CRUD API
  依存: #{101}
  範囲: 一覧・詳細・作成・更新・削除 API。画面は他の子
  完了条件: 各エンドポイントが契約どおり動く。401 は既存方針に従う
  テスト範囲: 自動 — 各動詞の成功。失敗経路: 自動 — 不正IDで 404

#{103} ユーザー一覧画面
  依存: #{102}
  範囲: 一覧・検索・ページネーション。編集画面は #{104}
  完了条件: 一覧が表示され、検索で絞り込める
  テスト範囲: 手動 — 検索とページ送り。目視 — 空一覧

#{104} ユーザー詳細・編集画面
  依存: #{102}
  範囲: 詳細・編集・削除 UI。一覧は #{103}
  完了条件: 詳細表示・更新・削除ができる
  テスト範囲: 手動 — 更新と削除。失敗経路: 手動 — 必須欠落で保存できない
```

検証が独立した機能構成になるときだけ、検証用の子を切る。親の `cargo test` を検証子へ丸投げしない。
