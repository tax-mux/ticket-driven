# 分割方針

## 子の本文は切り出し（プレースホルダ禁止）

親を精緻化したあと、子を薄いテンプレで作り直さない。**親の description を機能構成／セッション単位で切って配る。**

やる:

- この子が担う範囲・完了条件・影響範囲・テスト範囲だけを残す
- テスト範囲は **この子の完了条件** に対応させる（親の計画の丸コピー禁止）
- 失敗時・境界は、この子の振る舞いに必要なときだけ切って載せる
- 作成時点で `ticket-refine` の充足チェックとテスト範囲の合格ラインを満たす

やらない:

- `{なぜ必要か}` `{検証条件1}` のようなプレースホルダのまま作成する
- 親の本文を丸ごとコピーする
- 完了条件と「単体テスト」だけの薄い子を作り、着手時の精緻化に任せる

子の着手時の `ticket-refine` は **漏れ拾い**。split が充足していれば更新スキップ。

## 二段分割（必須）

| 段 | 軸 | 役割 |
|----|-----|------|
| 1 | **機能構成** | 親の範囲を能力境界で切る（プロダクトのまとまり） |
| 2 | **セッション完走** | 各片が「着手→実装→検証→Resolved」を **1エージェントセッション** で終えられる大きさか。事前指標で超えるならさらに切る |

機能構成だけで止めると、1セッションに収まらずへたりやすい。**第2段を省略しない。**

## 事前判定できる指標だけを使う

分割の必須／不要は、**起票・精緻化・分割の時点で description から数えられる／列挙できるもの**だけで決める。

使ってよい:

- 検証可能な完了条件（チェック項目）の **個数**
- 独自に検証できるまとまり（能力・画面・API・データ塊）の **個数**
- 影響範囲に書いた **中心パス／成果** の個数（「など」で曖昧な列挙は多めに数える）
- 範囲文に **種類の違う作業** が同居しているか（下記の同居禁止）

使ってはならない（必須トリガの根拠にしない）:

- 壁時計・所要分の見込み（予言不能）
- メッセージ数・トークン数の見込み
- 特定ハーネス名に依存する分岐

事後にへたった事実は **再分割** の材料にはしてよい（起票時の必須判定には使わない）。

## 障害・エラー修正の分割（推奨）

再現が書けたらすぐ親を立て、**現象確認 → 調査 → 解決** を子にする（起票の型は `ticket-create` の `bug-flow.md`）。

| 子 | 合格ラインの目安 |
|----|------------------|
| 現象確認 | 再現手順と期待／実際が検証可能。広いコード探索はしない |
| 調査 | 仮説と根拠。本線の大きな修正は入れない（同居禁止に注意） |
| 解決 | 修正＋確認子の DoD を満たす検証1系統 |

親はハブ。確認→調査→解決の順に依存を付ける。原因を特定し切ってから起票しない（調査は調査子の仕事）。

## 機械的必須トリガ（二段の前に見る）

次の **いずれか1つでも**当たる親は **分割必須**。`分割不要:` は書いてはならない（ユーザーが「分割するな」と明示した場合のみ例外）。

| # | 事前指標（数え方） | 既定動作 |
|---|-------------------|----------|
| A | 検証可能な完了条件（`- [ ]` 等）が **4個以上** | **必ず分割** |
| B | 独自に検証できるまとまりが **2つ以上**（能力／画面／API／データ塊など。各々に DoD を立てられる） | **必ず分割** |
| C | 明確な中心成果が **2つ以上**（例: 別API・別画面・別成果物。影響範囲の中心パスが互いに無関係な塊に分かれる） | **必ず分割** |
| D | 影響範囲の **中心ファイル／パスが4つ以上**（ディレクトリ丸ごと1つは1と数えてよい。ファイル列挙が4超なら分割） | **必ず分割** |
| E | **同居禁止**: 本線実装と、環境セットアップ（コンテナ起動・DB初期化・証明書等）が同一票の範囲に両方ある | **必ず分割**（セットアップと実装を別子へ） |
| F | **同居禁止**: 本線実装と、スキル作成／メタ作業（skill 追加・ハーネス設定だけの作業）が同一票にある | **必ず分割** |

例: DoD が5個の親（CORS / preflight / handshake 等が同居）→ A で分割必須。親のまま着手は HARD GATE 違反。

### 第1段: 機能構成単位

機能構成とは、プロダクト上のまとまりとして説明できる単位。層やファイルの切れ目より、**ユーザー／システムが得る能力の境界**を優先する。

| 良い分割（機能構成） | 避けたい分割 |
|----------------------|--------------|
| 認証、一覧、詳細・編集 | 「フロント半分」「バック半分」だけの層切り |
| モデル＋永続化、公開 API、画面 | ファイル1つずつの機械分割（検証不能なとき） |
| （大きいとき）コア実装と独立検証 | **DoD も検証手段もない**「手順1」「手順2」メモ分割 |

判定手順（第1段）:

1. 親の目的・完了条件を読み、構成要素（能力・画面・API・データ・検証）を列挙する
2. 各要素が **独自の検証可能な完了条件** を持てるか見る
3. 持てる要素が **2つ以上** → 候補にする（まだ起票しない）。**必須トリガ B/C** ならこの時点で分割確定
4. 1つにしかならない → 第1段はスキップし、第2段だけ見る

### 第2段: セッション完走上限（必須・事前指標）

各候補（または単一の親範囲）が、下の **子の合格ライン** を満たすか見る。満たさないなら、検証可能な途中成果でさらに切る。

**各子が満たすべき合格ライン（事前にチェック）:**

| 指標 | 合格 |
|------|------|
| 完了条件 | **1〜3個** |
| 中心成果 | **1つ**（または少数ファイルに閉じる1塊） |
| 検証 | 子の DoD に対応する手段が **1系統**（親や他子の未完に依存しすぎない） |
| 同居 | 必須トリガ E/F に当たらない |

| 良い分割（セッション） | 避けたい分割 |
|------------------------|--------------|
| User モデル＋バリデーション | CRUD API 全体を1子のまま |
| `GET` 一覧 API だけ / `POST` 作成だけ | 「バックエンド全部」 |
| 一覧の表示のみ → 検索・ページネは別子 | DoD なしの「手順1」「手順2」 |
| **途中成果に検証可能な DoD がある**ステップ | 完了条件の箇条書きを **検証不能なまま** 1行＝1子 |

メモだけのステップ分割は依然 NG。**途中成果に検証可能な DoD があるステップ分割は OK**（第2段の主手段）。

判定手順（第2段）:

1. 第1段の各候補（なければ親全体）を取る
2. 子の合格ラインを満たさない → 検証可能な小片に分解する
3. 小片が **2つ以上** → それぞれを子チケット化する
4. 合格ラインを満たす単一まとまり、かつ必須トリガ A–F に当たらない → 分割しない（親のまま着手可。`分割不要:` 必須）

### 補助基準（二段のあとで使う）

- **階層単位**: 同一能力の中で FE / BE / DB が独立に検証でき、かつ各片が子の合格ラインを満たすとき
- **ファイル単位**: 影響範囲が明確で、機能構成・合格ラインと一致するとき
- **ステップ単位**: 順序依存が強く、**各ステップに検証可能な DoD** があるとき（第2段と併用）

### 分割しない場合

次を **すべて**満たし、かつ必須トリガ A–F に **当たらない**ときだけ。親ジャーナルに `分割不要:` を残す（省略禁止。文言は `ticket-driven` の `journal.md`）。

- 子の合格ライン（DoD 1〜3・中心成果1・検証1系統・同居なし）を満たす
- 1回のコミットで完結する小さな変更、または同等の狭さ
- 依存が強く、切り離すとどちらも完了条件を検証できない（この理由を `分割不要:` に書く）
- ユーザーが「分割するな」と明示（必須トリガより優先）

**禁止**: 必須トリガ A–F に当たる親を「単一まとまり」と言って分割しないこと。

### 再分割（既存の子が粗いとき）

「すでに子があるから再分割しない」は **やめる**。次のとき再分割する:

- 未完了の子が **子の合格ライン** を満たさない（DoD≥4、中心成果が複数、同居禁止に当たる、など）
- 着手・実装中にスコープ膨張が description / DoD に現れた（事後でも指標は description 上で数え直す）

手順:

1. 粗い子を親とし、第2段で孫（または同階層の差し替え子）を切る
2. 粗い子の範囲をハブにするか、閉じる方針をジャーナルに1行残す
3. 作業単位は **細かい方** にする

足りないだけでサイズは合格ライン内 → 再分割せず、親または子のジャーナルに追記案だけ残す。

## 分割チェックリスト

- [ ] 必須トリガ A–F を事前指標だけで判定した（該当なら分割済み。`分割不要` で逃げていない）
- [ ] 壁時計・メッセージ数・特定ハーネス名を必須判定に使っていない
- [ ] 第1段が機能構成単位である（層・ファイル優先になっていない）
- [ ] 第2段で各子が合格ライン（DoD 1〜3・中心1・検証1系統・同居なし）を満たす
- [ ] 各子が独自の検証可能な完了条件を持つ
- [ ] 各子が `ticket-refine` の充足ラインを満たす（範囲・影響範囲・テスト範囲。プレースホルダなし）
- [ ] 各子のテスト範囲が子の完了条件に対応している（親のコピーではない）
- [ ] 依存関係が明確（必要なら relation 済み）
- [ ] 親の範囲を網羅し、重複がない
- [ ] 親チケットに `分割:` または（許可される場合のみ）`分割不要:` がある
- [ ] 実装は親ではなく（再分割後は）細かい子で着手する
