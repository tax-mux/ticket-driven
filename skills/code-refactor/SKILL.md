# コードリファクタリング

肥大化・深いネストを **実装中に予防**し、漏れは **実装直後に検討**する。

## 二段構え

| 段階 | 目的 |
|------|------|
| **実装中（予防）** | しきい値を超えるコードをそもそも書かない／押し上げない |
| **実装直後（セーフティネット）** | 触ったファイルだけ計測し、超過なら分割・浅化を検討 |

`ticket-driven` の日常フローでは両方を自動で行う（確認不要。実施は任意だが予防を優先）。

## トリガー

- チケット駆動の **実装ステップ**（予防を常時適用）
- ユーザーがリファクタ・分割・ネスト解消を依頼したとき
- レビュー・実装中に下記しきい値を超えた（超えそうな）コードを見つけたとき
- OpenCode / エージェントが保守性改善を提案するとき

## しきい値（必須検討）

次を超えたら **必ず検討**する（無条件に実施するわけではない）。

1. **600行を超えるソースコードは、機能構成単位でファイル分割を検討する。**
2. **ネストが５つを超えるコードはネストを解いて階層を浅くすることを検討する。**

## 実装中の予防（第一優先）

機能を足すときから次を守る。事後リファクタ前提の巨大差分を書かない。

1. **触る前に一瞥**: 対象ファイルの行数・ネストがしきい値近くなら、追記前に分割先／抽出先を決める
2. **増やさない書き方**
   - early return / guard clause
   - 長い分岐・ループ本体は関数に切り出す
   - 新規ロジックは既存ファイルを押し上げるより、責務が違うなら新ファイル＋薄い呼び出し
3. **超えそうならその場で小さく直す**: 今回の差分がしきい値超過を引き起こす／悪化させるなら、同チケット内で振る舞いを変えずに分割・浅化してよい
4. **混ぜない**: 仕様変更とリファクタは意図が分かる単位に分ける（同一チケットでも論理ブロックを分ける）

ジャーナルは通常不要。予防で大きめの分割をしたときだけ `リファクタ: 予防 — {要約}`。

## ワークフロー（事後検討）

```
対象を特定（今回触ったソースのみ）
 → 行数・ネスト深さを計測
 → しきい値超過なら検討メモを出す
 → 分割/浅化の方針を決める（または見送り理由を残す）
 → 実施する場合は振る舞いを変えずにリファクタ
 → 検証（既存テスト / 該当コマンド）
```

### 1. 計測

| 観点 | 目安 |
|------|------|
| 行数 | 対象ファイルの総行数（空行・コメント含む）。600行超で分割検討 |
| ネスト | `if` / `for` / `while` / `switch` / `try` / 関数・ブロック等の入れ子段数。5超で浅化検討 |

言語ツールがあればそれを使う。無い場合は目視・簡易カウントでよい。

### 2. ファイル分割（600行超）

機能構成単位で切る。

- 公開 API / エントリポイントと実装を分ける
- ドメイン単位（例: パース / 検証 / I/O / UI）で分ける
- 1ファイル1責務を目指す。ユーティリティの寄せ集めにしない
- 既存の import / 公開面を壊さないよう、re-export や薄い facade を許容する

分割見送りの例:

- 生成物・ロックファイル・データダンプ
- 単一の線形スクリプトで責務が既に明確
- 分割すると循環依存や公開 API が著しく悪化する

### 3. ネスト浅化（深さ5超）

代表手法（言語に合わせて選ぶ）:

- early return / guard clause
- 条件の抽出（ヘルパー関数・述語）
- ループ本体の関数化
- ネストした条件の平坦化（lookup / 戦略テーブル）
- 例外・エラーの一段処理への集約

浅化見送りの例:

- DSL / 状態機械で階層自体が仕様
- 浅化すると可読性が明らかに落ちる

### 4. 実施ルール

- **振る舞いを変えない**（バグ修正とリファクタを混ぜない）
- 差分は小さく、レビュー可能な単位にする
- 関連テストがあれば先に通す。無ければ最低限の手動検証手順を残す
- チケット駆動中なら、分割方針と検証結果をジャーナルに1行残す

## 出力テンプレート

```
## リファクタ検討
- 対象: {path}
- 行数: {n}（しきい値 600）
- 最大ネスト: {d}（しきい値 5）
- 方針: 分割 / 浅化 / 見送り
- 理由: ...
- 検証: ...
```

## 関連

- 日常フローへの組み込み: `ticket-driven`
- 差分確認: `git-diff`
- チケットの機能構成分割（精緻化の直後）: `ticket-driven` / `ticket-split`（ファイル分割と混ぜない）
