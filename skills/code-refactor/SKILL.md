# コードリファクタリング

ソースの肥大化・深いネストを検知し、分割・階層浅化を検討する。

## トリガー

- ユーザーがリファクタ・分割・ネスト解消を依頼したとき
- レビュー・実装中に下記しきい値を超えたコードを見つけたとき
- OpenCode / エージェントが保守性改善を提案するとき

## しきい値（必須検討）

次を超えたら **必ず検討**する（無条件に実施するわけではない）。

1. **600行を超えるソースコードは、機能構成単位でファイル分割を検討する。**
2. **ネストが５つを超えるコードはネストを解いて階層を浅くすることを検討する。**

## ワークフロー

```
対象を特定
 → 行数・ネスト深さを計測
 → しきい値超過なら検討メモを出す
 → 分割/浅化の方針を決める（または見送り理由を残す）
 → 実施する場合は振る舞いを変えずにリファクタ
 → 検証（既存テスト / 該当コマンド）
```

### 1. 計測

| 観点 | 目安 |
|------|------|
| 行数 | 対象ファイルの総行数（空行・コメント含む）。600行超で分割検討 |
| ネスト | `if` / `for` / `while` / `switch` / `try` / 関数・ブロック等の入れ子段数。5超で浅化検討 |

言語ツールがあればそれを使う。無い場合は目視・簡易カウントでよい。

### 2. ファイル分割（600行超）

機能構成単位で切る。

- 公開 API / エントリポイントと実装を分ける
- ドメイン単位（例: パース / 検証 / I/O / UI）で分ける
- 1ファイル1責務を目指す。ユーティリティの寄せ集めにしない
- 既存の import / 公開面を壊さないよう、re-export や薄い facade を許容する

分割見送りの例:

- 生成物・ロックファイル・データダンプ
- 単一の線形スクリプトで責務が既に明確
- 分割すると循環依存や公開 API が著しく悪化する

### 3. ネスト浅化（深さ5超）

代表手法（言語に合わせて選ぶ）:

- early return / guard clause
- 条件の抽出（ヘルパー関数・述語）
- ループ本体の関数化
- ネストした条件の平坦化（lookup / 戦略テーブル）
- 例外・エラーの一段処理への集約

浅化見送りの例:

- DSL / 状態機械で階層自体が仕様
- 浅化すると可読性が明らかに落ちる

### 4. 実施ルール

- **振る舞いを変えない**（バグ修正とリファクタを混ぜない）
- 差分は小さく、レビュー可能な単位にする
- 関連テストがあれば先に通す。無ければ最低限の手動検証手順を残す
- チケット駆動中なら、分割方針と検証結果をジャーナルに1行残す

## 出力テンプレート

```
## リファクタ検討
- 対象: {path}
- 行数: {n}（しきい値 600）
- 最大ネスト: {d}（しきい値 5）
- 方針: 分割 / 浅化 / 見送り
- 理由: ...
- 検証: ...
```
