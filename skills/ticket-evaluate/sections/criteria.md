# 点検観点

評価は **チケット記載の完了条件・範囲・テスト範囲** を正とする。チャット上の期待や「一般的なベストプラクティス」だけで不合格にしない。

## 必須（毎回）

| # | 観点 | 見ること |
|---|------|----------|
| 1 | DoD 対応 | 完了条件の各項目が実装・検証で裏付けられるか |
| 2 | 範囲 | 「やる」に収まり、「やらない」に踏み込んでいないか |
| 3 | 回帰・不変 | 不変と書かれた経路を壊していないか（該当テスト or 構造的ガード） |
| 4 | 検証 | テスト範囲どおり実行・結果が説明できるか。未実行なら評価ノートに明記 |
| 5 | 委任・影響 | 着手ノートの影響範囲・禁止事項との齟齬 |
| 6 | **コード品質** | 下記「コード品質（注意点レーン）」の短いチェック。合格／不合格の主軸にはしない |

## コード品質（注意点レーン）

**位置づけ:** DoD・範囲・回帰が正本。品質所見は原則 **注意点** に書く。一般論・好み・スタイルだけの不合格は禁止。

短い固定チェック（毎回・該当する項目だけ書く。問題なしなら「品質: 特記なし」1行でよい）:

| # | 観点 | 見ること |
|---|------|----------|
| Q1 | 秘密・署名 | 秘密の必須化／失敗クローズ。固定フォールバックや弱い既定値で本番署名可能になっていないか |
| Q2 | 失敗時の扱い | 握りつぶし／致命の境界が意図どおりか。ロールバックや非致命の方針が説明できるか |
| Q3 | テストの健全性 | フレークしやすい構成、断言が弱い、DoD を覆わない穴。安定再現できる指摘だけ書く |
| Q4 | 構造の匂い | 範囲逸脱の寄せ集め、既存機構を無視した平行実装（軽微なら非ブロッカー） |
| Q5 | **類似・重複** | 同種の処理・トークン／メール／バリデーション等が **別パスで作り直し**されていないか。既存ヘルパ／モジュールへ寄せられるのにコピペ横展開していないか |

**Q5 の見方（短く）:**

- 今回の新規ファイル・関数名／キーワードでリポジトリを検索し、**既存の近い実装**がないか確認する
- 「意図的な差分」（例: 保存前提トークン vs 自己完結トークン）があるなら、注意点に **差の理由** を1行。理由がなく二重化しているなら非ブロッカーで指摘
- 評価セッションでは統合・リファクタしない。指摘のみ（修正は別指示／別票）

**ブロッカーにするとき（品質由来）:** 秘密漏洩・失敗オープンで署名可能・明らかな回帰破壊・運用上すぐ危険、など **安全／データの実害** に直結する場合のみ。可読性・命名・好み・単なる重複は非ブロッカー。

**不合格の主軸にしない:** 品質指摘だけで `不合格` にしない。DoD 未達・範囲逸脱・回帰破壊が無いなら、品質は注意点に留め `合格` または `条件付き合格`（運用リスクが大きいとき）。

## UI があるとき（必須に昇格）

画面・フロント・見た目・操作フローに触れる票では、上に加え次を **必須** とする。バックエンドのみ・API のみなら省略可（省略理由を1行）。

| # | 観点 | 見ること |
|---|------|----------|
| U1 | **トンマナ** | 既存プロダクト／デザインシステムの色・余白・タイポ・コンポーネント感と揃っているか。新規だけ浮いていないか。ブランドやトーンの急変がないか |
| U2 | **ユーザビリティ** | 主操作が短いか。初見で迷わないか。ラベル／空状態／エラー／次の一手が分かるか。モバイル等の対象幅で破綻していないか |

詳細ヒューリスティックはスキル **`ui-critique`** の `sections/heuristics.md` を開く（本ファイルに全文を複製しない）。観察→判断→提案の順。感想だけで不合格にしない。

**証拠（先にチケット添付を見る）:**

1. **必須:** `redmine_issues` get で **`attachments` を確認**する（画面票で「無いと思ってコードだけ見る」は禁止）
2. 対象票に無ければ、ジャーナル言及の親／関連票の添付も見る（無ければ「関連も空」と評価ノートに書く）
3. スクショ／実機ログ／Playwright 結果が **チケット上にある** → それを根拠に U1/U2 と、画面到達系 DoD を判定する
4. **チケット上に画面証拠が無い**（attachments 空・同等のリンクも無し）:
   - DoD／テスト範囲に **画面到達・見た目・操作**（例: 合流リンク→画面、手動確認）が含まれる → 当該 DoD は **未達**。総合は **不合格**（コード／API だけ PASS でも `合格` / `条件付き合格` にしない）
   - 画面票だが DoD が API のみ等で UI 到達を要求しない → U1/U2 はコード読みで注意に留め、省略理由を1行。推測の UI 合格はしない
5. コード・CSS からの読み取りは **補足** に限定する。画面証拠の代替にしない

チケットの DoD／範囲に UI 品質が入っていない場合でも、添付があるなら見て、明らかなトンマナ崩れ・操作不能は **注意点** に書く（勝手に DoD を増やして不合格の主軸にしない。重大ならブロッカー）。

## 状況に応じて

| 条件 | 追加観点 |
|------|----------|
| トークン／署名／認証 | 秘密の必須化、期限、改ざん耐性、失敗時の扱い |
| メール／通知 | 宛先の解釈（要件文言との差）、既存送信機構の再利用、失敗の致命度 |
| API／ハンドラ配線 | 分岐ガード（例: 代行時のみ）、エラー時のロールバック方針 |
| Resolved 済み票 | close-audit 項目の抜け（DoD `[x]`、`ブースト:`、done_ratio 推移）を **プロセス注意** として書いてよい。合格判定の主軸は実装 DoD |

## 判定ラベル

| ラベル | 意味 |
|--------|------|
| **合格** | DoD すべて達成。注意点（品質含む）があってもブロッカーではない |
| **条件付き合格** | DoD は実質達成だが、解釈差分・テスト穴・運用リスク（品質ブロッカー手前の重大所見含む）が残る |
| **不合格** | DoD の未達、または範囲逸脱・回帰破壊がある（品質単独では不合格にしない）。**画面票でチケット上の画面証拠が無く、DoD／テスト範囲が画面到達・手動 UI を含むときも不合格**（上記 UI 証拠ルール） |

注意点は **ブロッカー / 非ブロッカー** を必ず分ける。
