# 評価ワークフロー

## 前提

- `issue_id` が分かっていること（ユーザー指定。無ければ確認してから開始）
- 作業ディレクトリは対象リポジトリ（チケットの影響範囲と一致）

## 手順

### 1. チケット取得（必須）

```json
{
  "action": "get",
  "issue_id": "{N}",
  "include": ["journals", "children", "relations", "attachments"]
}
```

読むもの:

- description: 背景・目的・**範囲**・**完了条件**・**テスト範囲**・影響範囲
- journals: `着手:` / `完了:` / 委任パック・実装パス・検証結果
- children / relations: 親ハブか実装票か、先行・後続
- **attachments:** スクショ・Playwright 結果など。画面票では **コードを読む前に** 有無を確認（`criteria.md` UI 証拠）

**禁止:** Redmine 未 get のまま「実装が分からない」と丸投げ。先に get。  
**禁止:** 画面票で添付未確認のまま「UI 実機未確認」と書いて `合格` / `条件付き合格` にする。

### 2. 対象の確定

| 票の形 | 評価対象 |
|--------|----------|
| 子チケット（実装単位） | **その子** |
| 分割不要の単一票 | **その票** |
| 親ハブ（子あり） | 親には書かない。評価する子を特定（ユーザー指定が無ければ未 Resolved 子 or 直近 Resolved 子を提案して確認） |

### 3. 実装の特定

優先順:

1. 完了／着手ジャーナルに書かれたパス・モジュール名
2. description の影響範囲
3. `git log` / `git diff`（ブランチや未コミット差分）。ジャーナルと食い違うときは **実ファイルを正** とし、差分を評価ノートに明記

見つからない場合:

- 票が New / 未着手なら「実装なし」と評価してよい
- 着手済みなのにパス不明なら、調査結果を `評価:` に書き、推測で合格にしない

### 4. 点検（criteria.md）

- DoD 各項目: **達成 / 部分 / 未達**＋根拠（ファイル・テスト名・挙動）
- 範囲逸脱の有無
- テスト: 記載どおり実行できたか、結果
- **コード品質**（`criteria.md` Q1–Q5）: 注意点レーン。類似・重複の横展開も含む。一般論だけで不合格にしない
- **UI があるとき**: トンマナ・ユーザビリティ（`criteria.md` の U1/U2）。詳細は `ui-critique` の heuristics。証拠はスクショ／Playwright／コード読み取り
- 注意点（セキュリティ・秘密鍵・宛先解釈・統合テスト欠落・プロセス欠落・品質所見など）

コードは **読むだけ**。フォーマット修正や「ついで修正」禁止。UI の改修も評価セッションではしない。

### 5. ジャーナル追記（必須）

`sections/journal-format.md` の `評価:` テンプレで **`notes` のみ** update。

```json
{
  "action": "update",
  "issue_id": "{N}",
  "notes": "評価: ..."
}
```

- status / done_ratio を同リクエストに **付けない**（合格でも Resolved にしない／不合格でも自分で差し戻し status を付けない）
- 原則、票は **レビュー** 状態。進行中・解決済みの再評価は理由を評価ノートに1行
- **不合格**のとき「次:」に実装側へ **レビュー→進行中の差し戻し** を明示する
- **合格**のとき「次:」に実装側のクローズ監査→レビュー→解決を書いてよい（評価側は実行しない）
- 追記後、必要なら get で最新 journal を確認（ACK だけに頼らない）

### 6. ユーザー報告

- 総合判定（合格 / 条件付き合格 / 不合格）を先に1〜2文
- DoD 対応の要点
- 注意点（ブロッカーか否かを区別）
- 「#N に評価コメントを追記済み」と明示

修正提案は「次にやること」として短く。実装は指示があるまでしない。
