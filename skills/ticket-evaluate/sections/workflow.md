# 評価ワークフロー

## 前提

- `issue_id` が分かっていること（ユーザー指定。無ければ確認してから開始）
- 作業ディレクトリは対象リポジトリ（チケットの影響範囲と一致）

## 手順

### 1. チケット取得（必須）

```json
{
  "action": "get",
  "issue_id": "{N}",
  "include": ["journals", "children", "relations", "attachments"]
}
```

読むもの:

- description: 背景・目的・**範囲**・**完了条件**・**テスト範囲**・影響範囲
- journals: `評価依頼:` / `分割:` / `分割不要:` / `着手:` / `完了:` / 委任パック・実装パス・検証結果
- children / relations: 親ハブか実装票か、先行・後続
- **attachments:** スクショ・Playwright 結果など。**実装評価**の画面票では **コードを読む前に** 有無を確認（`criteria.md` UI 証拠）

**禁止:** Redmine 未 get のまま「実装が分からない」と丸投げ。先に get。  
**禁止:** 画面票で添付未確認のまま「UI 実機未確認」と書いて `合格` / `条件付き合格` にする（実装評価）。  
**例外:** ジャーナルに `UI証拠なし: {理由} — 代替: …` があり理由が具体的なら、条件付き合格の検討可（`criteria.md`）。

### 2. 種別の確定（計画 / 実装）

| 手がかり | 種別 |
|----------|------|
| `評価依頼: 計画` / 「計画を評価」「分割を評価」 | **計画** |
| `評価依頼: 実装` / 「実装を点検」「#N を評価して」（着手後・レビュー） | **実装** |
| 未着手で実装パス無し | **計画** |
| それ以外 | **実装** |

### 3. 対象の確定

| 種別 | 票の形 | 評価対象 |
|------|--------|----------|
| 計画 | 親ハブ（子あり） | **親**（子の切れ方も見る。ノートは親へ） |
| 計画 | 分割不要の単一票 | **その票** |
| 実装 | 子チケット | **その子** |
| 実装 | 分割不要の単一票 | **その票** |
| 実装 | 親ハブ（子あり） | 親には書かない。評価する子を特定（ユーザー指定が無ければ未 Resolved 子 or 直近 Resolved 子を提案して確認） |

### 4a. 計画の点検（種別=計画）

コード差分は必須にしない。見るもの:

- 命題が実現内容まで展開されているか（DoD だけで薄くないか）
- 完了条件が検証可能か（曖昧・測れない文言がないか）
- 範囲・失敗時・テスト範囲が揃っているか
- 親 journals に `分割:`（子 ID 列挙）または適正な `分割不要:` があるか
- 子があるなら、各子がセッション完走サイズ／親の切り出しか（プレースホルダでないか）

判定: 着手してよいか。不合格なら「次:」に refine/split やり直しを書く。

### 4b. 実装の特定と点検（種別=実装）

優先順で実装パスを特定:

1. 完了／着手ジャーナルに書かれたパス・モジュール名
2. description の影響範囲
3. `git log` / `git diff`（ブランチや未コミット差分）。ジャーナルと食い違うときは **実ファイルを正** とし、差分を評価ノートに明記

見つからない場合:

- 票が New / 未着手なら種別を **計画** に切り替えるか、「実装なし」と書く
- 着手済みなのにパス不明なら、調査結果を `評価:` に書き、推測で合格にしない

点検（`criteria.md`）:

- DoD 各項目: **達成 / 部分 / 未達**＋根拠（ファイル・テスト名・挙動）
- 範囲逸脱の有無
- テスト: 記載どおり実行できたか、結果
- **コード品質**（`criteria.md` Q1–Q5）: 注意点レーン
- **セキュリティ**（`criteria.md` S1–S5）: 注意点レーン
- **UI があるとき**: トンマナ・ユーザビリティ。証拠はスクショ／Playwright／コード読み取り

コードは **読むだけ**。フォーマット修正や「ついで修正」禁止。UI の改修も評価セッションではしない。

### 5. ジャーナル追記（必須）

`sections/journal-format.md` の `評価:` テンプレで **`notes` のみ** update。**`種別: 計画|実装` を本文に含める**。

```json
{
  "action": "update",
  "issue_id": "{N}",
  "notes": "評価: ..."
}
```

- status / done_ratio を同リクエストに **付けない**（合格でも Resolved にしない／不合格でも自分で差し戻し status を付けない）
- **実装**: 原則、票は **レビュー** 状態。進行中・解決済みの再評価は理由を評価ノートに1行
- **計画**: New でも可。status は触らない
- **実装・不合格**のとき「次:」に実装側へ **レビュー→進行中の差し戻し** を明示する
- **計画・不合格**のとき「次:」に **着手禁止・refine/split** を明示する
- **合格**のとき「次:」に実装側の次アクションを書いてよい（評価側は実行しない）
- 追記後、必要なら get で最新 journal を確認（ACK だけに頼らない）

### 6. ユーザー報告

- 種別＋総合判定（合格 / 条件付き合格 / 不合格）を先に1〜2文
- DoD / 計画観点の要点
- 注意点（ブロッカーか否かを区別）
- 「#N に評価コメントを追記済み」と明示

修正提案は「次にやること」として短く。実装は指示があるまでしない。
